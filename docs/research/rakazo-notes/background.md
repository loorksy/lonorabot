# rakazo: long-running and background work

Source: `/home/user/elie222/rakazo` at commit `cd7e20e5da754d8d8deaf2780671ed34a38e2241`. All paths are relative to that repo root. "(implemented)" = I opened the code at the cited lines. "(stated)" = docs only.

## 0. The model in one paragraph

Everything a bot does is a **run** row in Postgres (`packages/db/prisma/schema.prisma:1224-1293`) with a `trigger` string (column at `packages/db/prisma/schema.prisma:1236`; values seen in code include `user`, `messaging` (`packages/adapters/src/wakeup.ts:29-38`), `routine`, `webhook`, `bot_message` (`packages/core/src/run-state.ts:29-35`), `helper`, `helper_result` (`packages/core/src/run-state.ts:108-109`), `cloud_agent` (`packages/adapters/src/cloud-agent-poll.ts:369`)). Background features are not separate engines: a routine tick, a background helper's result, a cloud coding agent finishing, and a reply from another bot each **create a new queued run** in a thread and let the normal executor pick it up. Timers and polling are graphile-worker jobs keyed by a `replaceKey` (`packages/adapter-kit/src/background-jobs.ts:90-105`). A 30-second reconciler re-enqueues run, routine-wakeup and other jobs from database rows, so for the job types I checked (runs, routine wakeups, helper/bot-message outcomes, cloud-agent polls) the job queue is not the source of truth (`packages/adapters/src/job-reconciler.ts:20`, `:383-395`, `:445-489`). I did not check every job type.

## 1. Routines (schedules)

### What a routine is
- A stored prompt plus triggers. Row fields: `name`, `prompt`, `crons[]`, `timezone`, `active`, `notify`, `webhookEnabled`, `githubEnabled`, `messageProvider`, `emailSenders`, optional model override, `watch`/`watchState`, `lastRunAt`, `nextRunAt`, `accountFailures` (`packages/db/prisma/schema.prisma:1489-1527`) (implemented).
- Docs definition: "A routine is a prompt a bot runs on its own: on a schedule, when something changes, or when another service calls it." (`docs/routines.md:3-4`).
- A routine run does **not** read the chat history: `runReadsThreadHistory` returns false for `routine` (`packages/core/src/run-state.ts:136-139`), and the executor passes empty messages for such runs (`packages/adapters/src/run-instructions.ts:449-458`). The run only sees the routine prompt (with skill references expanded, `packages/adapters/src/run-routines.ts:246-248`) plus memory/tools.

### Creation by the bot from chat
- Tool `schedule_create`. Description (verbatim, first four sentences; one more sentence follows): "Create a reminder or recurring job for this bot. Use for \"remind me in 10 minutes\" or \"every morning send a joke\". Repeats: cron or every/unit (min 1 minute), optionally from startAt. One-shot: runAt, delayMinutes, or delaySeconds." (`packages/adapters/src/builtin-tools.ts:1389-1391`).
- Companion tools `schedule_list`, `schedule_update`, `schedule_cancel` (`packages/adapters/src/builtin-tools.ts:1394-1428`; handlers `packages/adapters/src/run-tools-tasks.ts:209-261`).
- `createScheduleFromTool` validates, inserts the routine with `notify: true, active: true`, binds it to the originating thread, then enqueues a `routine.wakeup` job at `nextRunAt` (a `watch` schedule branches to a separate `createWatchFromTool` at `:517-519`, which I did not read). If the enqueue fails it deletes (or deactivates) the row and returns "Could not schedule the reminder. Try again." (`packages/adapters/src/schedule-tools.ts:482-565`).
- The validation runs before the approval card so an unsaveable routine shows no card (`packages/adapters/src/run-tools-tasks.ts:51-70`).
- Limits (implemented): 50 active routines per bot (`packages/adapters/src/schedule-tools.ts:455-456`, `:475-476`); duplicate active name in the same thread refused (`:468-474`); minimum repeat interval 1 minute (`:225`, `:231`; a cron is also checked by `validateRepeatingCron` at `:209-210`, body not read); one-shot must be in the future (`:181`); `delaySeconds` may be under a minute (`packages/adapters/src/builtin-tools.ts:155-158`).
- A routine run itself may create, list or cancel schedules but not update them (`packages/adapters/src/schedule-tools.ts:34-44`).

### Creation by the user
- UI flow: name, instruction, "Add trigger", optional per-routine model (`docs/routines.md:16-26`) (stated). API handlers `create`/`update`/`remove`/`testRun`/`history` exist (`apps/api/src/routes/routines.ts:57-64`, `:91`, `:336`, `:346`) (implemented; bodies not read in full).
- An active one-shot schedule cannot be created through the API form: "One-shot schedules must be created from chat." (`apps/api/src/routines.ts:23-27`; the check is `input.active && isOneShotRoutineCrons(...)`).
- Any space member may edit a routine; editing hands ownership to them, and queued-but-unstarted runs move to the new owner (`apps/api/src/routines.ts:131`; `packages/adapters/src/routine-handover.ts:6-23`).

### Triggers
- **Cron / interval / one-shot**: `routine.wakeup` job with `availableAt = nextRunAt` and `replaceKey routine:<id>`, so one pending wake per routine (`packages/adapter-kit/src/background-jobs.ts:98-105`).
- **Watch ("when something changes")**: checked without a model every `everyMinutes` (5 to 1440, default 15) (`packages/contracts/src/routine-watch.ts:22-25`, max at `:39`; tool text `packages/adapters/src/builtin-tools.ts:159-162`). Kinds: `files`, `command`, `tool`. On each tick `tickRoutineWatch` compares a fingerprint; only a change creates a model run, with a note appended to the prompt: "This run was started because something you watch changed (" ... "What changed since the last check:" (`packages/adapters/src/routine-watch.ts:700`, `:769-775`). No change: the next check is enqueued and, if `loud`, a system line "`<name> routine: no changes`" (or "`<name> routine: watching for changes`" for the baseline reading) is posted (`:777-794`). For a watch created or re-armed through the API the first reading is scheduled about 2 s later (`apps/api/src/routines.ts:76-79`); the chat-tool path was not read. Check timeout 60 s; computer provisioning timeout 5 min (`packages/adapters/src/routine-watch.ts:42-46`).
- **Webhook**: POST with a key (stated, `docs/routines.md:42-44`); body capped at 64 KiB (`apps/api/src/webhook-inbound.ts:12`); creates runs with trigger `webhook` (`apps/api/src/webhook-inbound.ts:333`). Details of auth not read.
- **Git event, Email, Slack message**: described in `docs/routines.md:46-63` (stated). Schema columns exist (`packages/db/prisma/schema.prisma:1504-1508`); I did not read `apps/api/src/email-inbound.ts` or `github-webhook.ts`.
- Docs note that webhook/outside-message runs follow stricter approval rules (`docs/routines.md:65-67`) (stated).

### Firing a tick (`wakeRoutine`)
`packages/adapters/src/run-routines.ts:131-349` (implemented):
1. Ignore if the routine is inactive, its space is being deleted, or `nextRunAt` no longer equals the job's `scheduledFor` (`:139-144`). This makes stale or duplicate jobs harmless.
2. If the job arrived early, re-enqueue for the right time (`:38-46`, `:145`).
3. Deactivated owner: skip this occurrence; a recurring or watching routine keeps its schedule, a one-time one is spent (`:146-165`). Archived bot: pause the routine (`:170-177`).
4. Watch routine: run the check first; return unless it changed (`:199-208`).
5. In one transaction: claim by updating `nextRunAt` to the next occurrence (or `active: false` when there is none, i.e. one-shot spent) conditioned on the old `nextRunAt` (`:218-236`); create `task` + `run` with `trigger: "routine"` (`:269-293`).
6. Enqueue `run.continue`; if that fails, only log, because "The committed run and advanced schedule are the durable source of truth" (`:305-320`). Append a `routine.fired` thread event (`:327-339`). Enqueue the next wakeup (`:340-348`).

### Missed runs (host was down)
- The reconciler re-enqueues a wakeup for every active routine whose `nextRunAt` is at or before now + 60 s (`packages/adapters/src/job-reconciler.ts:22`, `:445-458`, `:484-489`). So after downtime, each overdue routine fires **once**; the next occurrence is computed from the later of the scheduled time and "now" (`packages/adapters/src/run-routines.ts:122-129`; `packages/core/src/cron.ts:457-480`). Missed occurrences are not replayed one by one.
- Recurring timer runs carry a nonce `routine-timer:<routineId>:<scheduledFor>` (`packages/adapters/src/routine-coalescing.ts:4-7`). If an identical, completely unstarted tick is still queued, the new tick reuses it and cancels other pristine duplicates with reason `routine_coalesced` (`packages/adapters/src/routine-coalescing.ts:20-23`, `:39-66`, `:95-127`; call site `packages/adapters/src/run-routines.ts:251-267`). "Pristine" means no attempts, effects, steering, checkpoint, error or lease (`routine-coalescing.ts:48-65`).
- A timer run that first starts 15 minutes or more after its due time gets an extra instruction (verbatim): "This scheduled run started late: it was due ... and started ... Adapt anything that depends on the time of day to the actual time, skip steps that no longer make sense, and mention the delay when it matters to the user." (`packages/adapters/src/routine-lateness.ts:10`, `:51-60`; wired at `packages/adapters/src/executor.ts:410-420`, `:1586-1599`). The due time is stored in `runs.lateSince` (`packages/db/prisma/schema.prisma:1262-1263`) and shown in run history (`apps/api/src/routine-runs.ts:83`). Docs: "Late runs are never skipped" (`docs/run-execution.md:85-90`) (stated). Lateness is measured from the most recent occurrence due by the start time, not from the first missed one (`packages/adapters/src/routine-lateness.ts:5-9`, `:33-46`).

### Failure handling and backoff
- **One automatic retry** for a routine run stopped by a `TransientModelError`, 12 minutes later, only if the run made no tool call and posted no bot message (so nothing can be repeated), and only if the next scheduled occurrence is more than 30 minutes after the retry time (`packages/adapters/src/run-routines.ts:32-36`, `:57-96`). A run is retried at most once: `retryOfRunId` is unique (`packages/db/prisma/schema.prisma:1255-1256`). When the retry job fires, it is dropped silently if a later run of the routine exists (`run-routines.ts:397-401`); it is abandoned with a failure notice instead if the next occurrence is within 30 minutes, the routine is gone, paused (recurring only) or has changed owner, or the bot was archived (`run-routines.ts:402-417`).
- **Account backoff**: when the user's own model credential is refused (`model.ownCredential`; kinds `auth`, `access`, `key`, `credit`, `spending`, `model`), or the computer allowance is used up or the sandbox provider account is unusable, the routine's next run is pushed out by 5 min doubling per consecutive failure, capped at 24 h, or to the provider's stated reset time (`packages/adapters/src/routine-backoff.ts:8-10`, `:37-44`, `:59-64`, `:73-95`; call sites `packages/adapters/src/run-turn.ts:1116-1133`, `packages/adapters/src/executor.ts:925-938`). A successful run clears it (`routine-backoff.ts:101-130`; `run-turn.ts:934-936`). Rate limits and timeouts deliberately do not count (`routine-backoff.ts:46-50`).
- **Watch check failure**: a `RoutineWatchRetry` (per the constant's comment, "A busy or still-booting computer") retries in 60 s (`packages/adapters/src/routine-watch.ts:46`, `:730-738`). Any other failure pauses the routine and the bot posts (verbatim): "I paused the **<name>** routine because its change check failed: <reason>\n\nTell me how to fix it, or turn the routine back on once it's sorted." (`:739-763`).
- A routine with no parseable cron fires the already-due run once and then pauses instead of crash-looping (`packages/adapters/src/run-routines.ts:209-212`, `:229-233`).

### How results reach the user
- The run's final reply is posted as a bot message in the thread the routine was created in (`threadId` on the routine, falling back to the bot's own thread, `packages/adapters/src/run-routines.ts:179-197`).
- Silence is allowed. Prompt (verbatim): "If this routine's prompt says to stay silent when there is nothing to report, the entire final assistant reply must be exactly NO_RESPONSE — no surrounding prose, no variants, no progress updates, no all-clear, and no meta note that you are staying silent." followed by "Do not call message_user unless you have something to report." (`packages/adapters/src/run-replies.ts:18`; `NO_RESPONSE` constant `packages/adapters/src/silent-reply.ts:4`).
- Text written before a tool call is not posted as a mid-turn chat bubble for routine runs; its last segment is used as the final reply only when the model supplies none and has not chosen silence (`packages/adapters/src/run-replies.ts:28-36`). Tool status lines are also skipped for routine runs (`packages/adapters/src/run-turn.ts:312-314`).
- A routine completion marks the chat unread only when it produced text (`packages/adapters/src/run-notifications.ts:294-302`), and a push/in-app alert "<Bot> finished" with a 180-character preview is sent only then (`packages/adapters/src/run-turn.ts:958-974`; `packages/adapters/src/run-notifications.ts:19`, `:278-281`). Completion alerts also require the bot's `notifyOnFinish` setting or a group thread; the routine's own `notify` flag is consulted only for failures (`packages/adapters/src/run-notifications.ts:56`, `:80`).
- Failure: push "<Bot> failed" with the error text, governed by the routine's own `notify` flag (`packages/adapters/src/run-notifications.ts:38-41`, `:56`, `:80`; `packages/adapters/src/run-turn.ts:1134-1149`). No failure notice is sent while a retry is pending (`run-turn.ts:1134`, `:1140`).
- Run history: 20 per page (the first page a screen shows is 5, `packages/contracts/src/runs.ts:98-100`), each linked to the first message it posted; the code notes "Routine runs can finish silently" (`apps/api/src/routine-runs.ts:13`, `:58-71`; `packages/contracts/src/runs.ts:99`).

## 2. Wakeups / self-scheduling

- There is **no separate "wake me later" primitive**. `wakeup.ts` and `run-wakeup.ts` are the job queue and run dispatcher, not a bot tool (`packages/adapters/src/wakeup.ts:46`, `:207`; `packages/adapters/src/run-wakeup.ts:25`, `:137`, `:172`).
- A bot wakes itself by creating a **one-shot routine** with `schedule_create` (`delaySeconds`, `delayMinutes` or `runAt`; `packages/adapters/src/builtin-tools.ts:147-158`). When it fires the routine deactivates itself (`packages/adapters/src/run-routines.ts:122-129`, `:229-233`, `:340-345`).
- The system prompt tells the bot to do this for open loops (verbatim): "Do not wait to be asked about open loops. When something is left open until a known time, you may schedule_create one one-shot follow-up for then that checks the scratchpad item and stays silent if it is done, and record the follow-up's routineId in that item's notes. When the item is resolved, complete it and schedule_cancel its follow-up. Never follow up on something the user declined." (`packages/adapters/src/run-instructions.ts:250-251`).
- Because the follow-up runs as a routine and "cannot see the chat", the scratchpad item is the hand-off state between the chat turn and the later run (`packages/adapters/src/run-instructions.ts:245-249`). Scratchpad tools: `packages/adapters/src/run-tools-tasks.ts:84-141`.
- The run row also has `wakeAt` ("Durable retry schedule; null means runnable immediately when queued", `packages/db/prisma/schema.prisma:1257-1258`), written by the dispatcher when a run is enqueued (`packages/adapters/src/run-wakeup.ts:146-153`) and by requeue paths. I saw no bot tool that sets it, but did not search for one (unverified).

## 3. Background work while chat stays responsive

### Dispatch
- Runs start directly in the process that makes them due: `RunJobPublisher.enqueue` writes `wakeAt` on the row and calls `RunStarter.start`, which runs it as an independent task (or a `setTimeout` for a future time) (`packages/adapters/src/run-wakeup.ts:49-65`, `:144-155`). Docs: "No queue, scan, shared slot or notification sits between a due run and its start, so one slow or stuck run never delays another." (`docs/run-execution.md:8-9`).
- There is no fixed concurrency limit for runs; admission only checks memory headroom (physical and V8 heap vs. 4x the maximum attachment size), and only when the process already has at least one active run (`packages/adapters/src/run-execution.ts:7-35`, `:82-109`). A process that cannot admit a run publishes its id on a realtime topic `runs:ready` for another process (the transport behind `RealtimeFanout` was not read) (`packages/adapters/src/run-wakeup.ts:17`, `:84-89`, `:124-127`).
- Both API and worker construct a `RunStarter` (`apps/api/src/app.ts:349-352`; `apps/worker/src/index.ts:167-169`).
- Jobs other than `run.continue` go to the graphile-worker publisher (`packages/adapters/src/run-wakeup.ts:144-145`); those I saw enqueued are `routine.wakeup`, `routine.retry`, cloud-agent polls and messaging delivery. The worker runs three graphile hosts (which tasks each host takes was not read): interactive (concurrency from `GRAPHILE_WORKER_CONCURRENCY`, default 4), background (1), maintenance (100) "Long agent turns cannot occupy the capacity reserved for other workloads" (`packages/adapters/src/wakeup.ts:408-428`; `apps/worker/src/index.ts:246-248`). Poll interval 500 ms (`wakeup.ts:327`).
- Recovery scan every 5 s, interactive lane before the background lane (`routine` and `reaction` triggers), 100 rows per batch (`packages/adapters/src/run-wakeup.ts:218`, `:338-339`, `:352-358`).

### One bot, one computer, steering
- A bot's computer is held by one run at a time through an execution lease; a run that finds it held is requeued and started by the run that releases it (`packages/adapters/src/executor.ts:362-400`; `packages/adapters/src/run-lifecycle.ts:211-232`, `:343-372`).
- A user message that arrives while a conversational run is going joins that run as "steering" rather than waiting; it never steers a routine/background run (`packages/core/src/run-state.ts:141-162`). Docs: "A message sent while a run is going steers that run instead of waiting." (`docs/run-execution.md:25-26`).
- Consequence (my inference from the two points above and `docs/run-execution.md:25-28`, not traced end to end): a routine run holding the computer and a chat run of the same bot do not run at the same time; the chat message gets its own run which waits for the computer. Background helpers are the exception (below).

### Progress during long turns
Prompt for normal chat runs (verbatim, start): "Send progress updates only when the work will take minutes — long computer tasks or multi-step jobs — never for quick replies and never to announce that you are starting." (`packages/adapters/src/run-replies.ts:10-11`). `message_user` is the tool for mid-turn notes (`:14-16`).

## 4. Subagents

### Implemented
- Tool `run_subagent` (`packages/adapters/src/builtin-tools.ts:1540-1566`): "A helper, not a bot: no list entry, thread or computer. It ends with this turn unless background is set."
- **In-turn** (default): runs inside the parent turn; the parent waits. No nesting ("Subagents cannot nest further.", `packages/adapters/src/pi-runtime-subagent.ts:53`); at most 4 in parallel (`:32`, gate at `:54`, sized at `packages/adapters/src/pi-runtime.ts:304`); child tools exclude delegation tools (`:123-127`); optional per-call model (`:71-84`). Shown as a card with status running (`:62-69`) or failed (`:87-94`); the completed state is after the lines I read (docs list **Running**, **Completed**, **Failed**, `docs/groups.md:37-38`, stated).
- **Background** (`background: true`): `startBackgroundHelper` creates a hidden thread, a task and a queued run with trigger `helper`, plus a "running" card in the chat (`packages/adapters/src/background-helpers.ts:91-158`). Allowed only from a conversational turn in the bot's own app chat (so not a group thread), not from messaging channels and not from a helper-result turn (`:45-56`, error text `:74-77`). Cap: 4 active helpers per bot (`:99-106`, `:159-162`). The start is idempotent on `background-helper:<effectKey>` (`:82`, `:95-98`).
- The helper does not take the computer lease, so the parent bot stays free (`packages/adapters/src/executor.ts:335-341`, `:364-365`; `packages/adapters/src/run-recovery.ts:39-40`).
- Helper prompt (verbatim): "You cannot talk to the user, ask them anything, use the computer, or change memory, skills or routines. Finish with a concise result for the bot; name anything it should ask the user or change itself." (`packages/adapters/src/background-helpers.ts:179-188`).
- Tool result to the parent (verbatim): "Helper \"<name>\" is working in the background. End your turn now if nothing else needs doing; its result comes back to you later as a new message. Do not wait for it or check on it." (`:175-177`).
- When the helper ends, `returnHelperOutcome` settles the card and creates a **new run** in the original chat with trigger `helper_result` and a prompt that wraps the result as untrusted data (`:194-293`, `:306-319`). Result capped at 12,000 characters (`:27`). On failure the parent is told: "Tell the user briefly that it could not finish and why." (`:316-317`). The claim on `botOutcomeReturnedAt` and the creation of the new run are in one transaction, so each helper returns at most once (`:212-223`, `:279-293`) and is repaired by the reconciler after a crash (`packages/adapters/src/job-reconciler.ts:326-372`).
- System prompt guidance for the parent: `packages/adapters/src/run-instructions.ts:381-382`.
- Helper restrictions are enforced in code, not only in the prompt (implemented): a helper run is offered only an allowlist of nine read tools (`web_search`, `web_fetch`, `recall_memory`, `skill_read`, `task_catalog`, `scratchpad_list`, `board_tickets`, `ticket_get`, `cloud_agent_status`; `packages/adapters/src/run-tool-selection.ts:71-81`, `:166-167`); any other built-in tool name is refused at dispatch with "<name> is not available to a background helper. Don't retry; say in your result what the bot should do." (`packages/adapters/src/run-tools.ts:144-155`); a connector call runs only when every action is declared read-only (`packages/adapters/src/run-tool-gate.ts:195-203`); and a call that would need approval is not shown as a card (`packages/adapters/src/run-tool-gate.ts:568-576`, rest of that branch not read).

### Intended vs implemented (PRODUCT.md)
- `PRODUCT.md:27` marks the section "Status: intended behavior; implementation remains to be aligned."
- Intended (`PRODUCT.md:29-38`): one subagent behaviour with no foreground/background choice; subagents can take actions with normal tools and approvals; parent stays available.

## 5. Bot-to-bot work

- **`message_bot`**: asynchronous message to another bot in the same space; creates a run with trigger `bot_message` in the target's thread. Limits: 8,000 characters (`packages/core/src/bot-messages.ts:6`), hop limit 6 per chain, env `BOT_MESSAGE_MAX_HOPS` (`packages/core/src/bot-messages.ts:16-22`); on exhaustion, unless the message is a result/status going back to the bot that asked (`packages/adapters/src/bot-messages.ts:114-121`), the tool returns "bot-to-bot message limit reached for this chain; report back to the user instead of messaging another bot" (`packages/adapters/src/bot-messages.ts:121-127`). Delivery is replay-safe via a delivery key because "A tool call can be re-executed after a lease expiry" (`:131-133`). Tool result: "Delivery is async; a reply wakes you later as a new message. Continue independent work" (`:328`).
- The delegated bot's outcome is returned to the sender automatically, including on failure ("Could not complete the delegated request: <message>", `packages/adapters/src/run-turn.ts:940-951`, `:1100-1109`) and after a loop-guard stop (`:675-684`). The reconciler repeats this for runs whose return was lost (`packages/adapters/src/job-reconciler.ts:258-325`), with a fallback text "The delegated bot completed its turn without a written summary." (`:292-293`).
- `message_bot` is hidden inside group chats (`packages/adapters/src/schedule-tools.ts:46-57`).
- **Fleet tools** (`packages/adapters/src/run-tools-fleet.ts:145-255`): `create_space`, `spawn_bot`, `list_fleet`, `organize_bot`, `create_group`, `update_group`, `set_child_instructions`, `set_child_bot_model`, `create_child_routine`, `update_bot`. `create_child_routine` "Schedule a routine that wakes a bot in this space in its own thread" (`packages/adapters/src/builtin-tools.ts:1791-1793`). Listing caps: 200 bots, 100 groups, 100 sections, 60,000 characters (`packages/adapters/src/fleet-tools.ts:437-440`).
- Only runs the user started may use fleet tools; routine, webhook, bot-message and channel runs may not; subagents get none (`docs/fleet-management.md:16`, `:18-23`) (stated). In code, fleet tools are offered only when the bot's `fleetManagement` setting is on and the run is owner-started (`packages/adapters/src/run-tool-selection.ts:137`, `:168-169`) (implemented); which triggers count as owner-started is in `isOwnerStartedRun`, not read.
- **Groups**: 2 to 10 bots (`packages/contracts/src/domain.ts:196-197`). Docs and code differ in emphasis: `docs/groups.md:15` says "With no mention, the first bot in the group answers", while the prompt given to members says "This message went to every member of the group and names nobody ... Stay silent when it fits another member's description better, or when no member's description fits it and you are not the first member listed" (`packages/adapters/src/run-replies.ts:22`). So per the prompt each member decides, and the first member is only the fallback; the run row has a matching flag ("A group message that named nobody reached this member; it may end without a reply", `packages/db/prisma/schema.prisma:1243-1244`). ## 7. Proactive behaviour (does a bot speak first?)

Yes, in these implemented ways:
1. **Routine/one-shot results** posted to the chat, with a push when the bot's finish notifications are on (section 1).
2. **Self-set follow-ups** on open loops (section 2).
3. **Daily check-in** ("strategic initiative"): an hourly sweep (`packages/adapters/src/strategic-initiative.ts:83-85`) finds bots with `dailyCheckIns` on (default true, `packages/db/prisma/schema.prisma:996`), an open scratchpad item untouched for 12 h (`strategic-initiative.ts:23`, `:48-53`), no active computer-using run, no check-in in the last 24 h and no failed check-in in the last 7 days (`:20-22`, `:54-70`). The bot can switch it off with `update_bot` when the user asks (`packages/adapters/src/run-instructions.ts:376`). Items already covered by a pending one-shot follow-up are skipped (`:142-154`, `:165-168`). It queues a `routine`-trigger run with up to 5 items (`:24`) and this prompt (verbatim, part): "If no high-signal action is needed right now, the entire final reply must be exactly NO_RESPONSE. If action is needed, do only one concise proactive action: ask one blocking question or post one short update with a concrete next step. Do not repeat reminders that add no new information." (`:230-242`). Tools are restricted to `ask_user` and `message_user`, enforced at dispatch too (`:27`, `:197-212`). Its failure is not notified: "Nobody asked for a check-in, so its failure is not news to the user." (`packages/adapters/src/run-turn.ts:1135-1141`).
4. **Stuck-work reminders** (system, not model): a run sitting in `queued`, `waiting_input` or `waiting_takeover` for 4 h gets one push per waiting episode (for `waiting_input`: "<Bot> still needs an answer" / "This has been waiting on you."; for `queued`: "<Bot> is still queued"); at 24 h it is cancelled with a thread status line ("Stopped. This was still waiting for an answer.") and a "<Bot> stopped" push; a takeover wait expires after 30 min, before any reminder (`packages/core/src/stuck-work.ts:5`, `:9`, `:13`, `:63-73`, `:81-117`, `:123-125`; `packages/adapters/src/stuck-work.ts:54-134`, `:326-369`). Both pushes are sent only for a group thread or a bot with `notifyOnFinish` on (`packages/adapters/src/stuck-work.ts:159-161`, `:214`, `:358`). The reminder is claimed with a 2-minute TTL so a crashed push is retried (`packages/adapters/src/stuck-work.ts:46`, `:184-193`).
5. **Watch failure message** written in the bot's voice without a model call (section 1).
6. **Voice call escalation**: the call tool description allows ringing the user "when you have reminded them about the same thing three times and they have not replied" (`packages/adapters/src/builtin-tools.ts:1453`).

Notifications: completion pushes go to every space member (except for `bot_message` runs), failures and questions only to the run's user; snoozed chats suppress completions only (`packages/adapters/src/run-notifications.ts:87-96`, `:184-195`). ## 8. What survives a restart

### Durable state
- `runs` (status, lease owner/fence/expiry, `checkpoint`, `wakeAt`, `firstResponseAt`, `lateSince`, `botOutcomeReturnedAt`), `attempts`, `routines` (`nextRunAt`, `watchState`, `accountFailures`), `cloud_agents`, steering messages and external effects (relations at `:1270-1272`) (`packages/db/prisma/schema.prisma:1224-1368`, `:1489-1527`).
- graphile-worker jobs live in Postgres too, but are treated as rebuildable from the rows above (`packages/adapters/src/job-reconciler.ts:375-395`, `:484-502`).
- Timers in `RunStarter` are in-memory `setTimeout`s; they are lost on restart and replaced by the recovery scan reading `wakeAt` (`packages/adapters/src/run-wakeup.ts:56-64`, `:349-375`).

### Graceful stop (deploy)
- A stopping process claims no new runs (`packages/adapters/src/executor.ts:292-294`). In-flight runs are aborted via `shutdownSignal`, their computer checkpoint is flushed, and the attempt is not finalised (`packages/adapters/src/executor.ts:664-667`, `:1729-1737`, `:1975-1978`). The run is set back to `queued` with no error and re-enqueued: "no failure is recorded" (`packages/adapters/src/run-lifecycle.ts:310-341`). Shutdown aborts do not consume the setup-retry budget (`:466-468`).
- graphile jobs get up to 45 min to drain (`packages/adapters/src/wakeup.ts:205`, `:254-278`); Compose gives the worker `stop_grace_period: 50m` (`infra/compose/docker-compose.yml:500-502`).

### Crash
- A running run holds a 5-minute lease renewed every 60 s (`packages/adapters/src/run-lifecycle.ts:149-162`, `:413`; `packages/adapters/src/executor.ts:461-479`). If renewal fails the attempt aborts itself (`executor.ts:469-477`).
- After a crash the lease expires within 5 min; the 5 s recovery scan and the 30 s reconciler both pick up `leased`/`running` rows with expired leases (`packages/adapters/src/run-wakeup.ts:371-375`; `packages/adapters/src/job-reconciler.ts:219-225`), and `claimRun` takes it under a new fence (`packages/adapters/src/run-lifecycle.ts:378-444`). The old attempt may not open a model stream once it no longer owns the lease and fence (`:234-244`), and it aborts itself when a heartbeat renewal fails (`packages/adapters/src/executor.ts:467-478`); fencing of every individual write was not traced.
- In the worker, only the process holding reconciliation leadership runs a pass (`packages/adapters/src/job-reconciler.ts:180`; leadership passed at `apps/worker/src/index.ts:251-254` via `createPostgresReconciliationLeadership`; lock constants described as an advisory lock at `packages/adapters/src/job-reconciler.ts:29-32`; the lock implementation itself was not read). Leadership is optional in the reconciler (`deps.leadership &&`). The API process creates a reconciler only with the in-memory job driver (`apps/api/src/app.ts:640-641`).
- Side effects are guarded against repetition on the second attempt: tool calls "Claim the effect to execute it, or return what an earlier attempt already settled" (`packages/adapters/src/run-tool-gate.ts:123-124`). Example of the result given to the model when the outcome is unknown: "An earlier attempt to send this email was interrupted and may or may not have gone out. Tell your owner instead of sending it again." (`packages/adapters/src/run-tools-email.ts:378`). Progress messages from earlier attempts are known to the new attempt (`packages/adapters/src/run-progress.ts:40`).
- Paused turns (waiting for an answer, approval or screen takeover) are stored as a versioned transcript checkpoint with the pending tool call id and resumed from it (`packages/adapters/src/turn-checkpoint.ts:20-37`, `:43-57`). A paused turn whose tool is no longer available fails with "A tool this paused task was using is not available, so it cannot continue. Start the task again." (`packages/adapters/src/run-lifecycle.ts:170-178`).

### Resumed vs failed
- Resumed: queued runs, runs with expired leases, paused runs, routine schedules (via `nextRunAt`), cloud-agent polling (via `nextPollAt`), unreturned helper and bot-message outcomes, unsent routine-failure notices (exhausted `routine.retry` jobs are kept as "durable notice requests", `packages/adapters/src/wakeup.ts:455-506`).
- Failed: a run whose setup fails 8 times in a row (`packages/adapters/src/run-lifecycle.ts:167-168`, `:485-500`); computer-busy and DB-saturation waits retry without limit and do not count (`:469-470`, `:181-183`). Setup retry delays: 250 ms doubling with the run's fence to at most 8 s (the formula's 10 s cap is never reached because the exponent stops at 5) (`:199-201`); provider outage 15 s doubling to a 5 min cap (`:203-209`).
- Cancelled: stuck work at 24 h / 30 min (section 7).

### What the user is told
- Graceful restart or crash recovery: nothing explicit that I found; the run continues and the reply arrives later. `firstResponseAt` is preserved across attempts (`packages/db/prisma/schema.prisma:1259-1260`).
- Operators (not users) get a `run.queue_delayed` error log when a queued run (trigger not `routine`/`reaction`, and not waiting behind its own bot's computer) is due and unstarted for 30 s (`packages/adapters/src/run-wakeup.ts:18`, `:262-303`).
- Otherwise the user-visible signals I found are failure pushes, the 4 h reminder and the 24 h cancellation text; I did not search the web/mobile clients for others.

## Weaknesses and risks seen in this area

1. **Large amount of concurrency machinery.** Leases, fences, three graphile hosts, a direct starter, a 5 s scan, a 30 s reconciler with advisory-lock leadership and a legacy-queue migration path (`packages/adapters/src/wakeup.ts:19-21`, `:79-95`; `packages/adapters/src/run-wakeup.ts:172-221`; `packages/adapters/src/job-reconciler.ts:375-395`). This is sized for multi-tenant, multi-process hosting. A single-owner product does not need most of it.
2. **Direct writes to graphile-worker private tables** (`graphile_worker._private_jobs`, `_private_tasks`) for moving, pruning and reading jobs (`packages/adapters/src/wakeup.ts:84-93`, `:129`, `:464-472`, `:536-548`). This couples the code to a library's internal schema.
3. **Watch routines of kind `command` run a shell command every interval "without a model or per-run approval"** (`packages/adapters/src/builtin-tools.ts:162`). A command that succeeds but is costly or has side effects repeats up to every 5 minutes until someone notices (a failing check pauses the routine, see next item). There is a guard for some protected commands (`commandWatchGuardError`, `packages/adapters/src/run-tools-tasks.ts:60-61`, `:212-213`; its rules were not read).
4. **One watch-check failure pauses the routine** and waits for the user (`packages/adapters/src/routine-watch.ts:739-763`). For a non-technical owner the monitor stays off until they act on that chat message; the message includes the raw `reason` text (the error's `message`, `:739`). Whether a push accompanies it was not checked.
5. **Routine failure pushes carry the run's error string as the body** (`packages/adapters/src/run-routines.ts:98-119`; `packages/adapters/src/run-turn.ts:1142-1148`). How user-friendly that string is depends on how the error message is built (`userRunError` and related code), which was not read.
6. **Only one retry, and only for transient model errors with no tool call yet** (`packages/adapters/src/run-routines.ts:57-96`). A routine that fails after its first tool call is not retried until its next occurrence; a one-shot reminder in that state is simply lost apart from the failure push.
7. **Routine runs have no chat context** (`packages/core/src/run-state.ts:136-139`). A reminder created with a vague prompt ("do what we discussed") will fail to do the right thing; correctness depends on the model writing a self-contained prompt and scratchpad notes.
8. **Daily check-in is on by default** and costs a model run per eligible bot per day (`packages/db/prisma/schema.prisma:996`; `packages/adapters/src/strategic-initiative.ts:20`). Eligibility is a substring match of routine ids inside free-text scratchpad notes (`:166`), which is fragile.
9. **50 active routines per bot at a 1-minute minimum interval** is a high ceiling for unattended model spend (`packages/adapters/src/schedule-tools.ts:455-456`, `:225`).
10. **Crash recovery can take up to 5 minutes** (lease length) before a run restarts, and I found no user-visible "I was interrupted, continuing" message (`packages/adapters/src/run-lifecycle.ts:413`). Whether the model turn restarts from the beginning after a crash is not confirmed (see below); if it does, non-effect work is repeated and paid for twice.
11. **Stuck waits are cancelled after 24 h** (`packages/core/src/stuck-work.ts:9`). A question the owner did not answer for a day is dropped with "Stopped. This was still waiting for an answer."; the task is not resumed automatically.
12. **Docs lag code** in at least two places in this area: `PRODUCT.md:42-43` (background helpers described as a proposal) and `docs/groups.md:15` (who answers in a group).
13. **Background helpers are read-only by a hard-coded allowlist** (`packages/adapters/src/run-tool-selection.ts:71-81`) plus three other enforcement points (section 4). This is the gap PRODUCT.md calls out (`PRODUCT.md:42-43`): the helper cannot act, so every action still waits for a later parent turn. The restriction lives in four places (prompt, tool selection, dispatch, gate), which is easy to get out of sync.
