## 1. Headline findings

**B1 (BUG). The runtime deletes the recovery hints the tools write.** Any result with `ok: false` gets `result["recovery"] = recovery` (`packages/agent-runtime/src/lonora_agent/environment.py:210`), where `recovery` is the generic classifier output (`packages/agent-runtime/src/lonora_agent/environment.py:36`, `packages/agent-runtime/src/lonora_agent/environment.py:37`). `observe` runs on every result (`packages/agent-runtime/src/lonora_agent/tool_block.py:300`) before the model's tool message is built (`packages/agent-runtime/src/lonora_agent/tool_block.py:358`). Tools in these families write their own `recovery` text under the same key, so it never reaches the model. Ran `observe` on the real constants: `owner_profile_requires_owner_message`, `incoming_call_device_required`, `memory_too_large`, `memory_authority_claim_refused`, `owner_prefers_other_channel` and `consult_budget_exhausted` all came back with `"recovery": {"category": "terminal_domain_failure", "next_action": "alternate_route", ...}` and the written sentence gone. Hints under another key (`guidance`, `next_tool`, `candidates`, `closest_lines`) survive, and so does `recovery` when the handler did not set `ok: false` (agent_create's `agent_market_ambiguous`). The tool policy tells the model to "follow typed recovery information" (`packages/agent-runtime/resources/constitution/tool-policy.md:7`); for most failures that information is the two words `alternate_route`.

**B2 (OVER-CAUTION BY DESIGN, order-dependent refusal). Recalling history first disables the owner's own request.** The docstring states the intent: once the run has read something someone else wrote, "the sensitive tools ... fall back to the owner's card or refusal" (`packages/tools/src/lonora_tools/restrictions.py:97`, `packages/tools/src/lonora_tools/restrictions.py:104`). It is therefore not a coding slip; the defect is that nothing tells the model (or the owner) that the order matters. The external set is wider than listed below: it also holds `artifact_read`, `workspace_read`, `search_internal`, `news_feed_read`, `subagent_inspect` and `collaboration_inspect` (`packages/agent-runtime/src/lonora_agent/context/run_evidence.py:54`, `packages/agent-runtime/src/lonora_agent/context/run_evidence.py:55`, `packages/agent-runtime/src/lonora_agent/context/run_evidence.py:59`, `packages/agent-runtime/src/lonora_agent/context/run_evidence.py:63`, `packages/agent-runtime/src/lonora_agent/context/run_evidence.py:67`, `packages/agent-runtime/src/lonora_agent/context/run_evidence.py:68`), and another agent's message that arrived after the owner's message in the thread also counts (`packages/tools/src/lonora_tools/restrictions.py:90`). `owner_message_id` returns None once the run has read "external content" (`packages/tools/src/lonora_tools/restrictions.py:114`), and `session_search`, `consult_model`, `agent_inspect`, feeds, calendar and every `web_`/`mcp_`/`search_` tool count as external (`packages/agent-runtime/src/lonora_agent/context/run_evidence.py:60`, `packages/agent-runtime/src/lonora_agent/context/run_evidence.py:65`, `packages/agent-runtime/src/lonora_agent/context/run_evidence.py:69`, `packages/agent-runtime/src/lonora_agent/context/run_evidence.py:62`, `packages/agent-runtime/src/lonora_agent/context/run_evidence.py:72`; marked at `packages/tools/src/lonora_tools/registry.py:506`). So in one owner turn: search past chats, then try to save what the owner just said to USER.md -> `owner_profile_requires_owner_message` (`packages/tools/src/lonora_tools/memory.py:123`); change reach-me -> `owner_preferences_require_owner_message` (`packages/tools/src/lonora_tools/memory.py:206`); create the agent he asked for -> a card to tap (`packages/tools/src/lonora_tools/agents.py:213`); revoke supervision -> `supervision_revoke_requires_owner_message` (`packages/tools/src/lonora_tools/supervision.py:503`). The rule is needed for safety (injected text must not stand for the owner), but no tool result, description or policy tells the model that the order matters, while the policy says "First recover prior answers" (`packages/agent-runtime/resources/constitution/tool-policy.md:15`) and `session_search` is the core recall tool (`packages/tools/src/lonora_tools/session_search.py:59`). Safe fix direction: say so in the refusal and in the gated tools' descriptions ("call this before any search/read of others' text"), or snapshot the owner-message standing per call instead of per run for tools whose arguments quote the owner's message.

**B3 (the owner's gold case, inside this group).** Two symbol resolvers exist. `agent_create` uses `symbol_candidates`, which accepts a broker suffix ("XAUUSD.r", "XAUUSDm": `packages/tools/src/lonora_tools/agents.py:55`, `packages/tools/src/lonora_tools/agents.py:72`). Everything else uses `catalog_symbol`, exact or case-only (`packages/tools/src/lonora_tools/symbols.py:12`), and raises a bare `symbol_not_found` (`packages/tools/src/lonora_tools/symbols.py:15`). In this group that hits the grant card (`packages/tools/src/lonora_tools/owner_actions.py:85`) and, silently, relationship evidence (`packages/tools/src/lonora_tools/relationships.py:66`). The read-only lookup that fixes it exists (`market_symbols`, `packages/tools/src/lonora_tools/market.py:40`) but no failure names it. The system prompt does say "Use market_symbols to discover exact symbols before guessing aliases." (`packages/agent-runtime/resources/system/lonora.md:212`) and `trading_context.md` repeats it (`packages/agent-runtime/resources/prompts/trading_context.md:5`); but ran the live registry: `market_symbols` has no eager profile, so it is discovery-only (callable only through `tool_call`), and the production trace shows it was not among the 23 native tools offered (`production-trace.md:20`). Confirmed by the trace for the broker code: in run 1ae9a14c `market_instrument` on `XAUUSD` returned `broker_account_not_found` although `list_accounts` had been called and the connection id passed correctly (`production-trace.md:95`, `production-trace.md:238`, `production-trace.md:248`). Separately, the MetaApi adapter turns any non-candles 404 into `broker_account_not_found` (`packages/adapters/src/lonora_adapters/brokers/metaapi.py:57`, `packages/adapters/src/lonora_adapters/brokers/metaapi.py:58`), which is the second code in the owner's quoted reply.

**B4. A raised error reaches the model as a bare code.** `LonoraError` becomes `{"ok": false, "code": <code>}` (`packages/agent-runtime/src/lonora_agent/tool_dispatch.py:113`); only argument errors add `issues` (`packages/agent-runtime/src/lonora_agent/tool_dispatch.py:115`). The classifier then adds one of 13 `next_action` words: `inspect_existing_state` for any `*_not_found` (`packages/agent-runtime/src/lonora_agent/environment.py:81`), `reload_authoritative_state` for `version_conflict` (`packages/agent-runtime/src/lonora_agent/environment.py:47`), `respect_scope` for the permission list (`packages/agent-runtime/src/lonora_agent/environment.py:69`), else `alternate_route`. No result names the tool that would fix it (every recovery block carries `schema_tool: tool_environment`, a constant default: `packages/contracts/src/lonora_contracts/tool_environment.py:31`; the production trace shows it on the gold failures, `production-trace.md:246`, but it points at schema inspection, not at a fix). The reply filter does not stop codes: "Public capability names and ordinary diagnostic vocabulary are not credentials" (`packages/core/src/lonora_core/public_reply.py:3`). So the cheapest thing for the model is to repeat the code to the owner and ask.

**B5 (BUG, wrong word). A timed-out non-financial mutation is later refused as `broker_result_ambiguous`.** A mutation that hits its 90 s deadline returns `tool_execution_uncertain` (`packages/agent-runtime/src/lonora_agent/tool_dispatch.py:127`); that code is in the AMBIGUOUS set (`packages/agent-runtime/src/lonora_agent/environment.py:17`), so the route is marked ambiguous (`packages/agent-runtime/src/lonora_agent/environment.py:159`) and every later identical call in the run returns `broker_result_ambiguous` with `reconcile_before_any_resend` (`packages/agent-runtime/src/lonora_agent/tool_dispatch.py:70`, `packages/agent-runtime/src/lonora_agent/tool_dispatch.py:73`). For `memory_write`, `peer_send`, `task_start`, `owner_notify` this is a broker word about a non-broker action; only read-only, non-ambiguous routes ever expire (`packages/agent-runtime/src/lonora_agent/environment.py:121`). Ran `observe` + `blocked_route` for `memory_write`: the route is blocked with `ambiguous: True`. A second trigger the first draft missed: a mutation whose call was interrupted (worker restart) and that is not replay-safe returns `tool_execution_uncertain` without running (`packages/agent-runtime/src/lonora_agent/tool_dispatch.py:82`; ran the live registry: `peer_send`, `task_control`, `routine_create`, `subagent_spawn`, `collaboration_start` and `ticket_start` are not replay-safe, `memory_write`, `task_start`, `owner_notify` are). Recovery the model is not told: verify with the matching read (`memory_read`, `task_inspect`, `subagent_inspect`) and resend if absent.

**B6. Doc vs code: where owner preferences go.** The constitution says "Store stable user preferences and verified durable facts in MEMORY.md" (`packages/agent-runtime/resources/constitution/memory-policy.md:1`). The code says the opposite: USER.md is "owner profile all Agents share; only what the owner said" (`packages/tools/src/lonora_tools/memory.py:278`) and a whole-document write with a user section is refused with "Owner preferences belong in the shared owner profile" (`packages/memory/src/lonora_memory/commit.py:29`). The system prompt agrees with the code, not the constitution: "USER.md is the owner profile all Agents share (language, length, tone, reach-me, standing rules); write only what the owner said." (`packages/agent-runtime/resources/system/lonora.md:449`). The code wins: a preference saved per the constitution lands in one agent's private MEMORY.md and the other agents do not read it (MEMORY.md is "your knowledge", `packages/tools/src/lonora_tools/memory.py:279`).

## 6. LEAKS: how internal codes, ids and English strings reach the owner

1. **Bare codes are the only content of most failures** (`packages/agent-runtime/src/lonora_agent/tool_dispatch.py:113`) and the reply filter passes them (`packages/core/src/lonora_core/public_reply.py:3`). There is no table from code to an owner-language sentence in these families. This is the direct source of "رجعت **symbol_not_found**".
2. **Wrong-domain code**: `broker_result_ambiguous` for memory, tasks, peers, notifications (B5, `packages/agent-runtime/src/lonora_agent/tool_dispatch.py:73`).
3. **Wrong-cause code**: `broker_account_not_found` for a missing symbol or any other non-candles 404 (`packages/adapters/src/lonora_adapters/brokers/metaapi.py:58`); `tool_not_allowed` for a misspelled tool name (`packages/tools/src/lonora_tools/registry.py:353`).
4. **Codes returned as data the model is expected to summarise for the owner**: participant `error_code` in `collaboration_inspect` (`packages/tools/src/lonora_tools/collaboration.py:77`); `error_code` per run and `reason_code` in `agent_inspect` (`packages/tools/src/lonora_tools/supervision.py:297`, `packages/tools/src/lonora_tools/supervision.py:152`); `recent_observations` (tool name + code) in `runtime_status` (`packages/tools/src/lonora_tools/runtime_control.py:50`); `reason_codes` in relationship evidence (`packages/tools/src/lonora_tools/relationships.py:82`); Task `failure.code` in `task_inspect` (`packages/contracts/src/lonora_contracts/tasks.py:24`).
5. **Owner notification text is not filtered.** `owner_notify` stores the model's `summary` as the notification (`packages/db/src/lonora_db/attention.py:428`); `public_reply_violation` is applied to `wait_for_input` questions (`packages/tools/src/lonora_tools/runtime_control.py:75`) but is not referenced anywhere in `packages/db/src/lonora_db/attention.py` or `packages/tools/src/lonora_tools/incoming_call.py` (grep). A summary with a code, a UUID or a path would be shown as written. UNSURE: whether the web UI sanitises attention text on render.
6. **Internal ids in results**: `connection_id` in `list_accounts` (`packages/tools/src/lonora_tools/account.py:53`), agent ids, `owner_action.id` (`packages/tools/src/lonora_tools/owner_actions.py:190`), run ids. The guidance says "never transport IDs as account numbers" (`packages/tools/src/lonora_tools/account.py:64`) but says nothing about `connection_id` itself; if the model prints one, the reply filter replaces the UUID with `[REDACTED]` unless it is in the run's public id set (`packages/core/src/lonora_core/public_reply.py:10`, `packages/core/src/lonora_core/public_reply.py:48`), which the owner then sees as a technical artefact.
7. **English server sentences addressed to the model** sit in results the model summarises: `note` (`packages/tools/src/lonora_tools/incoming_call.py:30`), `guidance` (`packages/tools/src/lonora_tools/account.py:63`), `next` (`packages/tools/src/lonora_tools/agents.py:197`). They are instructions, not owner text; risk is paraphrase into the reply. Low.
8. Exception text does not leak: unknown exceptions log only the type (`packages/agent-runtime/src/lonora_agent/tool_dispatch.py:132`) and broker diagnostics stay in the log. Stored results are redacted (`packages/tools/src/lonora_tools/tool_results.py:35`). No secret path found in these families.
