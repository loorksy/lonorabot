# Signed device authorization

Super Bot is a capability of the existing Agent and TradingGoal, not another runtime. The normal `super_bot_propose` tool creates a durable pending request. It never grants authority. The chat card reviews the exact account, broker symbol, plan steps, execution mode, volume/action ceilings and manual-position permission. The owner registers a passkey after account-password reauthentication, then signs a fresh activation challenge using the platform's WebAuthn user verification. Lonora stores public credential material, never a device PIN, biometric or private key.

The server binds each short-lived challenge to the authenticated owner/session, pending request and immutable permission hash. It verifies origin, relying party, credential signature, presence and user verification. A used proof can reread the current result after a lost response; it cannot reactivate a stopped, replaced or revoked grant. Plan changes disable autonomy. Expansion requires a new proposal and proof; reductions, pause, stop and the existing Emergency Stop remain available without new device authentication. Stopping a capability does not close positions.

Advisory plans cannot execute financial steps. A supervised background wake prepares the existing durable approve/reject card; actual approval is checked again before broker mutation. Autonomous plans require the signed active grant and existing global trading controls, preflight, account serialization, operation identity, journal and reconciliation. Activation does not enable global Trading or send an immediate trade. The existing Gateway scheduler dispatches one durable observe-only work Run for a verified activation. It reads the same saved Goal and actual account/market tools through the normal runtime; its real result returns once to the originating conversation or authorized group. The shared live-state projection reports pending authorization, current Goal state and the actual review status/error; activation review cannot trade or resume a blocked Goal. Richer risk-budget and complete financial orchestration remain tracked in the implementation matrix. Existing unsigned autonomous goals are disabled by migration `0027_device_authority` and require a reviewed authorization.

## Public native bindings

Web requires the configured HTTPS `LONORA_ALLOWED_ORIGIN` (localhost HTTP is permitted for development). Android uses `react-native-passkeys` and the OS Credential Manager; iOS uses the platform passkey implementation. New native code requires a new compatible binary once; the existing fingerprint-based OTA mechanism must not deliver it to an old binary.

Set `LONORA_PASSKEY_ANDROID_FINGERPRINTS` to a JSON list of the actual installed APK signing-certificate SHA-256 fingerprints, using colon-separated hexadecimal bytes. These fingerprints are public. `LONORA_PASSKEY_ANDROID_PACKAGE` defaults to `ai.lonora.mobile`. Set `LONORA_PASSKEY_IOS_APP_IDS` to the public Apple `TEAMID.bundleIdentifier` values. The API serves `/.well-known/assetlinks.json` and `/.well-known/apple-app-site-association`; Expo config declares the matching webcredentials domain. Android assertion origins are accepted only for configured certificate hashes, never values supplied by the client. Empty bindings explicitly disable native activation, while offering the secure Web flow without putting bearer tokens in URLs.

Verify the metadata on the public origin, install the correctly signed new binary, and test an OS prompt on real devices before claiming native acceptance. Browser virtual-authenticator tests verify actual WebAuthn creation/assertion and server state, but cannot certify native behavior or a production domain association. Test cancellation, lockout/unsupported devices, session expiry, a changed plan, rejection, lost response, revocation and reload. No device error should grant authority.

## Local acceptance

`tests/check_device_authority.py` uses genuine ES256 signed assertions against disposable PostgreSQL and production verification functions. `tests/check_goals.py` covers supervised approval through the normal ToolRegistry and simulation executor, plus autonomous closed-loop/recovery safety. `tests/web/goals.spec.mjs` uses Chromium's virtual CTAP2 authenticator with verified user presence. `tests/mobile/device-authority.spec.mjs` exercises durable review/rejection in Expo Web. Native device acceptance remains an explicit separate check.
