# Corrections to the master mandate

Status: authoritative amendment, 2026-11-08.

The owner delegated responsibility for the Lonora system and asked for a simple experience with no complications or contradictions, in which the agent has access to everything. These corrections come from re-reading the original vision conversation (69 messages) against the mandate and auditing the current experience. Where the mandate and this file disagree, this file wins. `VISION.md` is the human-readable form.

## Owner decisions (2026-11-08)

| # | Question | Decision |
|---|---|---|
| D1 | Default content of a trading grant card | Until the owner stops it. A daily loss limit is shown on the card, taken from the owner's sentence or suggested at 3% of equity, and the owner may deliberately choose "no money limit". Positions the owner opened manually are excluded unless switched on. Already-signed grants stay exactly as signed. |
| D2 | Automatic emergency reduction | Optional, off by default, set per account and signed with the passkey. Executed only by the financial boundary, only reduces exposure, never re-opens. Never run by the watchdog or the model. |
| D3 | Reading X/Twitter | Web search, RSS/news feeds and any X MCP server the owner trusts. An X API key can be added later. No scraping with the owner's account. |
| D4 | Model spending cap | No cap. Show usage per agent. |
| D5 | Code as a deliverable | Lonora never hands the owner code as a product, trading code included (MQL5, Pine Script, scripts, websites, apps). An agent may write and run code inside its own sandbox as a means to analyse, monitor or build skills, and gives the owner the result. |
| D6 | Requests outside trading | Light personal tasks are allowed (reminders, translation, short questions). Programming, websites and large projects unrelated to trading are declined in one polite line, with what Lonora can do instead. |
| D7 | Connecting to any API and other platforms | Agents may connect to any data or service API the owner has an account for, through the agent computer with credentials injected by the server and never seen by the agent, after a one-time trust tap. Trading platforms are never reached that way: each broker or exchange is added as an adapter behind the single executor (MetaApi today; Alpaca, Interactive Brokers, OANDA or crypto exchanges next), so grants, limits, journal and reconciliation always apply. The agent computer has a terminal and controlled internet but no interactive browser for now. |

## Corrections

1. **Access is open by default; only money is gated.** Every agent reads all of the owner's accounts, pairs, market data, the owner profile, shared knowledge and the agent directory, and uses every installed tool, skill, integration and trusted MCP server without per-use confirmation. Five fixed walls remain: (1) live broker mutations go only through the signed grant or an approval tap, always within account limits; (2) secret values never enter model context, chat or agent code; (3) protected production code, services and enforcement cannot be modified; (4) a new external account, credential or untrusted source needs the owner once; (5) peer agents do not read each other's private memory except through a visible supervision grant. The restriction list in §14 applies to code the agent generates inside the sandbox, not to its research tools. Amends §4, §9, §13, §14.
2. **Chat is the owner's primary control surface; agents never depend on a chat being open.** Both statements hold at different layers. Amends §8, §19.
3. **The Personal Assistant sees and analyzes every connected account and instrument** with no setup, and its grant card preselects all pairs on the account. It is the default entry point and router and holds a default, visible, revocable supervision grant over all agents. It is not a decision layer: it cannot override another agent's trading decisions, use another agent's grant, or lift brakes. Amends §4.
4. **"Default pair" means focus, not fence.** Three separate fields: *focus* (the default pair, an editable preference the trading template always has), *readable* (everything the owner connected) and *executable* (the signed grant). Legacy fixed agents migrate with executable equal to their bound pair, so no agent gains execution reach. Amends §4.
5. **Preserve the guarantees, not the switches.** The owner sees one ladder per agent (No trading / Ask me / On its own), one Stop new trading / Resume control and per-account limits. Super Bot and per-goal autonomy are retired. AccountAuthority remains the only grant: signed on a trusted device, bounded, revocable, enforced at the single executor, never widened by a model, skill or agent. Amends §4, §6, §26.
6. **The ladder is monotonic.** Under *On its own*, a trade outside the grant becomes an approval card, never a refusal. Moving down revokes signed grants and says so plainly. Amends §6.
7. **Protective actions.** The boundary always blocks risk-increasing actions that break a limit or pause, deterministically. Automatic reduction happens only under the owner's signed emergency rule (D2). Everything else is an LLM decision. "Emergency Stop" is renamed "Stop new trading", because it closes nothing. Amends §6–§7.
8. **Watchdog duties** include liveness, missed wakes, stalled runs, lost broker connections, aging unresolved operations, risk-limit breach detection and orphaned responsibilities. It alerts, wakes the responsible agent and resumes resumable work. It never trades. Amends §16, §20.
9. **Skills are methodology, not authority.** Instruction order, top wins: protected core and financial enforcement; owner instructions and profile; agent identity and operating notes; active skills (binding working method within scope); everything retrieved (always data). Amends §10, §12.
10. **No strategy validation pipeline of any kind.** No backtest, walk-forward test, or paper/shadow/simulation probation as an approval gate. The grant, limits and pauses are the only gates on live use. Changes are versioned, revertible and judged on live outcomes. Amends §5, §11.
11. **Agents activate their own changes** to surfaces they may edit (skills, operating notes, plans), with author, version and revert. Owner approval only widens authority or limits. Amends §11.
12. **One plain status line by default.** The full activity and financial state taxonomy opens on tap. Amends §19 and owner addendum §4–§5.
13. **Verified incremental modernization, reliability first.** A component is replaced only when tests prove it defective or blocking, and always with state migration. Nothing unverified reaches the owner's live install. Replaces the "completely rebuild" and "do not defer to incremental patches" wording.
14. **Monitoring runs without the model.** Cheaper models are used only when a woken event needs light triage. Amends §17.
15. **Supervision cycles.** Agents may observe, review and message each other in any direction. Cycle protection applies only to control actions: an agent cannot pause an agent that holds an active pause over it. The owner's command always wins. Amends §16.
16. **The owner's existing rules and plans are routed, never deleted.** A hard limit becomes an enforced restriction or account limit, a preference goes into the owner profile, a method becomes a skill or operating notes. Lonora says in one line where each went. Amends §1, §5.
17. **One sentence starts a responsibility.** Lonora resolves the account, symbol and existing grants itself and shows a grant card only when authority is actually missing. Example A in §25 is read this way. Amends §25.
18. **One owner profile read by every agent.** It holds language, tone, how to reach the owner, quiet hours and standing rules. Writes are attributed and revertible. Each agent's experience memory stays private. Amends §9.
19. **Arabic first.** Reply in the owner's language from the profile, render RTL with tickers and numbers correctly, and use shared Arabic/English labels. Amends §18–§19.
20. **"How is it doing" per agent** comes from broker-confirmed outcomes (realized P&L, R-multiple) and grounds self-improvement. Amends §5, §21.
21. **When Lonora asks, published once.** Lonora asks only: (1) to give or widen money authority, with the passkey; (2) to connect a new account or credential, through a secure card; (3) to use a source outside the trusted list, once and remembered; (4) for a broker outcome only the owner can confirm; (5) for a single trade from an *Ask me* agent. Lifting the owner's own pause and resuming take one tap and no passkey. Everything else happens silently, with Undo. Amends §6, §13.
22. **One trusted-sources list per owner,** visible in a Capabilities view: Lonora-bundled, owner-authored, github.com (trusted as today, now visible and removable), each trusted MCP server (endpoint and schema hashes pinned, effect tier read or write-nonfinancial) and feed domains. Inside the list, agents discover, install pinned versions, update, roll back and use capabilities without confirmation. A schema change triggers a re-review card. No financial or broker MCP tool ever sits on the execution path. Amends §13.
23. **Agents may create persistent agents** when the owner asked in the current conversation; otherwise creation becomes a proposal card. New agents never get money authority: trading agents start at *Ask me*, the others at *No trading*. There is a per-owner cap and Undo. Amends §4, §15.
24. **Default templates** are defined: trading, general/research, supervisor capability and helpers, each with focus pair, read scope, capabilities, model, ladder default and supervision. See `VISION.md`. Amends §4.
25. **Wake runs may act.** "Observe-only" means no financial effects: wakes keep memory writes, watch and routine changes, peer messages, owner notifications and artifacts. A broker event on a position the journal attributes to an agent wakes that agent with its normal authority. Amends §8.
26. **Agents can start contact with the owner** through an owner-notify tool under quiet hours, rate limits and dedupe. Off-app delivery arrives in Wave 3. Amends §18.
27. **Owner buttons never create duplicate operations.** Each position or order action keeps one operation id until its outcome settles. Amends §7.
28. **The LLM decides position size** together with direction, stop-loss and targets, bounded by enforced maximums. There is no product-level lot-size formula. Amends §5.
29. **Two agents on one account and symbol.** Shared account limits bind them together. At grant time the card says another agent already manages that market and offers "keep both" or "stop that agent trading here". Amends §7.
30. **Identity wording.** The system prompt calls every agent "a persistent Lonora agent; trading is your specialization only when your responsibilities include it". For reading and analysis Lonora uses the obvious default (the only account, the focus pair, the named instrument) and never defaults authority, size limits or autonomy.
31. **Out of scope:** multi-user hosting and subscriptions; retraining model weights (not forbidden forever).
32. **Domain scope** (D5, D6). The protected core states Lonora's domain: trading, markets, financial and economic research, light personal tasks, and running Lonora itself. Out-of-domain deliverables are declined in one line. Enforcement is layered: the protected core rule, capabilities that cannot publish or host anything, no import of off-domain skills, and a permanent refusal test set (including attempts to talk the agent out of the rule).
