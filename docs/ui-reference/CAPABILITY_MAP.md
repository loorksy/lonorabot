# Capability map: Lonora-Desktop-37 reference UI against the backend at `ab16645`

## Summary

1. 175 elements of `Lonora-Desktop-37.html` are mapped against the backend at `ab16645`, in five phase tables (2 to 6), with 38 contradictions recorded, 54 owner questions and 9 backend work packages (WP-A to WP-I).
2. By status: 80 `bind` (the backend already serves it), 38 `build_backend` (route, contract, table or event to add), 39 `ui_only` (client work, no server data), 13 `owner_question` (blocked on an answer), 5 `dev_only` (kept out of production).
3. By phase: phase 2 layout, lists and sheets 56 elements (12 bind, 15 build_backend, 27 ui_only, 1 owner_question, 1 dev_only); phase 3 conversation 66 (37 bind, 16 build_backend, 8 ui_only, 4 owner_question, 1 dev_only); phase 4 agent and domain pages 24 (17 bind, 4 build_backend, 2 owner_question, 1 dev_only); phase 5 settings, onboarding and usage 21 (10 bind, 2 build_backend, 3 ui_only, 5 owner_question, 1 dev_only); phase 6 calls 8 (4 bind, 1 build_backend, 1 ui_only, 1 owner_question, 1 dev_only).
4. Phase 1 (this PR) delivered the reference tokens (`packages/ui-tokens/src/reference.{ts,css}`: both themes, glass and depth, radii, motion, opaque-glass fallbacks) and the icon set with pair icons (`packages/ui-web/src/icons`) in commit `9f79327`, plus this map; no screen is restyled yet.
5. The largest backend gap is per-owner conversation state: unread counts, read cursor, pins, mute, archive, favourites and custom lists exist only in the prototype's localStorage (WP-A, WP-B; 13 elements), followed by unified search (WP-C), the conversation conveniences (reactions, suggestions, commands, guests, voice notes: WP-D, WP-E), the trading and status projections the chat needs (WP-F) and the generative-UI vocabulary (WP-G).
6. Money-safety contradictions to settle before building: the offline auto-resend (C1), the ResolveCard «غير معروف» semantics (C11), edit-and-resend deleting history (C21) and undoing a tightened stop (C24); the server keeps its semantics until the owner answers OQ1, OQ11, OQ20 and OQ30.
7. Owner-decision contradictions: the mandate defaults vs D1 (C18), the quota card and usage budget vs D4 (C22), the per-agent trading switch vs the server brake (C14), the general-agent ladder vs the trading-only ladder (C19), the research template vs `Agent.role` (C5), the blur filter vs the motion rule (C9), the silent recording vs «nothing faked» (C29).
8. Server-model contradictions concentrate in phases 4 and 5: authentication (C30), chart drawing tools (C31), schedules (C33), knowledge (C34), goals (C35), Telegram (C38) and prototype copy that describes device-local storage (C36).
9. The agent-pages reader result reached this step truncated after two elements; phases 4 to 6 were compiled directly from the reference and the API survey and must be re-read against the reference before each phase starts (see «How this map was built»).
10. Verification is side by side: the reference and the app in the same states at 390x844 and 1280x800, dark and light, pixel-diffed per element, with structural, gesture and data-truth assertions in Playwright, gated per phase (see «Verification plan»).

## The owner's rules, restated

`docs/ui-reference/Lonora-Desktop-37.html` is the single source of truth for how the new `apps/web` looks and behaves: the phone layout under 900px and the desktop layout at 900px and above, dark and light, spacing, radii, colours, fonts, icons, motion, gestures and every loading, empty and error state. The UI is not changed or simplified to fit what the backend has today; the backend is changed to serve the UI. Every element of the reference, including the ones it only mocks (localStorage state, demo replies, simulated timings), becomes real: through the existing contracts and hooks where they exist, through new backend support where they do not. Nothing is hidden behind a capability flag and nothing is faked. One exception: the avatar component stays Lonora's (`packages/ui-web` `AgentAvatar`/`GroupAvatar` with `packages/core` avatar state and motion), placed and sized wherever the reference shows an avatar. `packages/ui-tokens` stays the single source of tokens; there is one Composer and one Message component; Lingui serves Arabic first then English with RTL direction isolation; accessibility follows the reference; motion is restricted to `transform`, `opacity` and `clip-path`. Out of production (dev-only): plans and subscription, «معرض الواجهات», the lab «مختبر الحالات» and mail approvals. Agent types derive from `Agent.role` and `scope_mode`. Permissions follow the server ladder (analysis / supervised / autonomous plus `AccountAuthority`; the reference calls them «دون تنفيذ» / «تنفيذ بموافقة» / «تنفيذ مفوَّض»). Trading ON/OFF and the stop control stay as the server defines them («إيقاف الصفقات الجديدة» / «استئناف»). Contradictions, inside the reference or between the reference and a money-safety invariant (no trade without a signed grant or an approval tap; secrets never shown to agents or stored in chat; uncertain operations never resent; agents cannot widen authority or lift owner brakes) or an owner decision (D1 grant defaults, D2 emergency reduction, D3 X/Twitter, D4 no spend cap, D5 no code deliverables, D6 light personal tasks only, D7 API connections through the agent computer), are recorded here as owner questions and never decided silently.

### How this map was built

- Three readers worked on the reference in parallel against the worktree at `ab16645`: the shell and lists (routes, `lonora_db`, contracts, web hooks, with 390x844 and 1280x800 screenshots in dark and light), the conversation surface (behaviour and timings taken from the reference's own code), and the agent, group and domain pages (rendered with Playwright at 390x844 dark). The first two results arrived complete. The third reached this step truncated after its first two elements (`agent.page.hero`, `agent.page.avatar-editor`); the remaining rows of phases 4, 5 and 6 were compiled directly in this step from the reference's `page()` routes and functions (`updatesPage`, `usagePage`, `tradePage`, `odLog`, `wtRows`, `integrationsPage`, `profileExtras`, `supSection`, `agentTypePage`, `brokerFormPage`, `accountPage`, `avatarSheet`, `callPage`, the settings pages, `#auth`, `#lock`, `installSheet`) and from the API survey (`apps/api/src/lonora_api/routes/*.py`, `packages/contracts`, `packages/db/src/lonora_db/schema.py`). Those rows carry the same columns but are shorter, and the first task of phases 4 to 6 is to re-read their pages against the reference before building.
- The reference's notes block (the 52k-character comment inside `<script>` starting "UI reference for the React + TypeScript app") was read in full: tokens, data model, component map, behaviour rules, timings, "WHERE THINGS LIVE" and the v34 to v36 rules.
- Status vocabulary used in every table: `bind` (the backend has it; the UI binds to the existing route, contract or hook), `build_backend` (the UI needs a route, contract, table, migration or event that does not exist), `ui_only` (pure client work, no server data), `owner_question` (cannot be built until the owner answers the numbered question), `dev_only` (kept out of production per the owner's list).
- Phases: 1 capability map and tokens/icons (this PR: `packages/ui-tokens/src/reference.{ts,css}`, `packages/ui-web/src/icons`, this document); 2 layout, lists and sheets; 3 conversation; 4 agent and domain pages; 5 settings, onboarding and usage; 6 calls. Each table lists the elements the phase builds; an element used by several phases sits in the phase that first needs it and is referenced by id elsewhere.

## Verification plan

The reference is checked against the app side by side, state by state, with Playwright (chromium, `/usr/bin/google-chrome`, the repository's `playwright.config.mjs` for the app and a file URL for the reference, as the readers did in `scratchpad/work/ui1/*/shots.mjs`).

1. **Fixtures.** One seeded database per phase (agents Lonora, a gold trading agent with an account, a research agent, a general agent, one group; messages of every kind; one pending approval, one ambiguous operation, one watch, one restriction; attention items; routines; artifacts; usage rows) so the app can reach every state the reference shows. The reference is driven into the same states through its own `S` state and `handle()` actions (sign-in bypass, lab toggles for offline/slow/maintenance, seeded cards), never by editing its markup.
2. **Viewports and themes.** Every screen is captured at 390x844 (phone, `isMobile`, `hasTouch`, DPR 2) and 1280x800 (desktop), in dark and light, with `prefers-reduced-motion` off and on where motion matters. Screenshots are saved as `<phase>/<element-id>--<viewport>--<theme>--<state>.png` for the reference and the app and compared with a pixel diff (`pixelmatch`) per pair; a diff above the threshold fails the element. Thresholds: 0.1% of pixels for static layouts, with explicit allow-lists for areas that legitimately differ (the avatar component per the owner exception, live timestamps, real data values).
3. **Per element.** Each row of the phase tables becomes a Playwright spec that (a) puts the app in the state the «Reference behaviour» column describes, (b) asserts the structural facts that screenshots cannot (ARIA roles and labels, focus order, `aria-live` regions, history entries after Back, `aria-busy` during loading, `role=alert` on errors), (c) exercises the gesture or timing (long-press 430ms, pull-down filters, pager swipe with velocity, sheet drag thresholds) through `page.mouse`/`page.touchscreen` and checks the resulting class/state, and (d) takes the side-by-side screenshots. Timing assertions check spring settle windows (e.g. 300–340ms) by sampling transforms, not by waiting for mocked timers.
4. **Data truth.** For every `bind` and `build_backend` element the spec also asserts that what the screen shows came from the API (network interception on `/api/*`: the unread count equals `inbox.unread_count`, the status line equals `agent-status.ts` for the returned state, the order line matches the journal row) and that no placeholder or timer-driven value is rendered. Dev-only surfaces are asserted absent from the production build (`import.meta.env.DEV` gates) and present in the dev build.
5. **Per phase.** Phase 2: shell, lists, search, sheets and states across the two viewports, including the pager hand-off (ghost vs real page pixel-identical), selection mode, archive and lists, every skeleton and state page. Phase 3: the conversation with every message kind, the composer and its menus, the trading cards against the seeded approval/operation, streaming (`run.delta` replay), reconnect. Phase 4: every agent and domain page with its skeleton, empty and error states, the chart sheet detents. Phase 5: settings pages, integrations sheets, usage with seeded `ln_usage` rows, the auth screens that ship (OQ35), the lock. Phase 6: call screen, capsule, strip and incoming call against the simulation voice provider. Mobile parity for shared contracts (WP-A, WP-D, WP-E) runs the existing `tests/mobile` suite plus new specs for the changed fields.
6. **Gates.** A phase PR passes when: the side-by-side diffs pass for every element of the phase at both viewports and both themes; the Playwright web suite and the Python checks for the phase's work packages pass on a fresh `*_test` database; `pnpm lint` and `pyright`/`ruff` pass; the i18n catalogs compile for `ar` and `en`; axe-core reports no serious violations on the captured screens; the contradictions and owner questions touched by the phase are either answered (and the answer recorded here) or the element stays out of the build.
