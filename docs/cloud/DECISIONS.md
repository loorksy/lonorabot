# Lonora Cloud — owner decisions

Each decision has a recommendation. Status is `Proposed` until the owner confirms it, then `Confirmed (date)` or
`Changed (date): <what>`. A Claude Code session that needs a `Proposed` decision asks the owner and records the answer
here in the same pull request. "Blocks" names the first task that cannot start without it.

## Product and architecture

| ID | Decision | Recommendation | Why | Blocks | Status |
|---|---|---|---|---|---|
| D1 | Isolation unit per customer | **One VM per customer** running the existing production stack. Dense container cells are a later, cheaper tier (Phase 9) after a security review. | The workspace runs arbitrary agent code with egress and setuid-class capabilities; a shared kernel beside other customers' broker credentials is not acceptable for a trading product. The installer and `lonora` CLI were built for one owner per server. | P3-T1 | Proposed |
| D2 | Where the control plane lives | **New repository `loorksy/lonora-cloud`.** | Different security boundary (it knows every customer) and release cadence; the Lonora `Dockerfile` copies `packages/` whole, so in-repo code would ship inside every customer image. | P2-T1 | Proposed |
| D3 | Cloud provider for the customer fleet | **Hetzner Cloud** to start (API, firewalls, volumes, snapshots, EU + US + Singapore). Behind a provider driver interface so DigitalOcean/AWS can be added. Verify current prices and the provider's acceptable-use terms for agent workloads. | Lowest cost per GB of RAM among API-driven providers; VM-per-customer makes RAM the main cost. | P3-T2 | Proposed |
| D4 | Edge and TLS | **Cloudflare proxied DNS + one Cloudflare Origin CA certificate per VM + Authenticated Origin Pulls**; firewall accepts 443 only from Cloudflare ranges. | Avoids Let's Encrypt per-registered-domain issuance limits at signup volume, adds DDoS/WAF, hides origin IPs. Trade-off: Cloudflare terminates TLS. Alternative: DNS-only + Caddy ACME with several issuers. | P1-T3 | Proposed |
| D5 | Domains | Owner picks and registers the cloud domain. Placeholders used in this plan: `<handle>.lonora.app` (customer), `my.lonora.app` (portal), `admin.lonora.app` (staff, behind Zero Trust), `status.lonora.app`, `lonora.app` (marketing). | — | P3-T3 | Proposed |
| D6 | Model access | **The customer's own keys or own subscription**: the customer enters their own provider keys in their Lonora, or signs in with their own ChatGPT plan through OpenAI's official Sign in with ChatGPT where it is offered (VISION §12, Amendment 4; until OpenAI approves Lonora Cloud for remotely hosted apps, Cloud installations run with `LONORA_CHATGPT_SIGN_IN=off` and offer keys only). Claude subscriptions are not offered (Anthropic does not permit them in other apps). Platform-managed model credits are not offered. | The earlier owner decisions "D4" and "Q22" recorded in docs/usage-dashboard.md (not this table's D4) forbid spend caps and budgets; managed credits would need them. Also keeps zero access. | — | Confirmed (2026-11-22) |
| D7 | Signing in to a customer's Lonora | **One sign-up (owner, 2026-11-27).** On Lonora Cloud (D48) the website account that asked for the installation becomes its owner with the password it signed up with: `customer.sh create` hands the website's salted hash to the new installation, which replaces it with its own hash at the first sign-in. No setup link, no second sign-up, and no SSO: each side checks the password itself. A self-hosted install, or `customer.sh create` run by hand, still uses the one-time setup link. | The owner rejected signing up twice. Staff still never know the password. Trade-off: for as long as the website account exists, a leak of the website database exposes a salted hash (PBKDF2-SHA256, 100,000 rounds) of the password the customer uses in Lonora. A website password may be 10 characters, so Lonora's sign-in takes any length; setting a password there still needs 12. | P1-T4, PW-T7 | Confirmed (2026-11-27) |
| D8 | Recovery keys (backup key, `LONORA_ENCRYPTION_KEY`) | **Escrowed**, encrypted on the VM to a KMS public key; decryption needs two staff approvals and is audited. Customer-managed keys (no escrow) offered later on Max/Enterprise. | Without escrow a lost VM is a lost customer. Honest trade-off: escrow means the company could, with dual control, recover a customer's data. | P3-T7 | Proposed |
| D9 | One app for self-hosted and cloud | **One mobile app**; cloud customers connect with the portal's "Open in the app" link or its QR code (D36). | One store listing, one review, one codebase. | P1-T8 | Proposed |
| D10 | Workspace backups | **Workspace on its own attached volume**, provider snapshots (daily Pro/Max, weekly Starter). `lonora backup` stays as is for database, artifacts and config. | `lonora backup` deliberately excludes the workspace (up to tens of GB). | P6-T2 | Proposed |
| D11 | Update window default | **Weekend window while forex is closed** (Saturday, customer's time zone); customer may choose another window. Security fixes may go sooner with notice. Customers trading 24/7 instruments (crypto CFDs) pick their own window. | A gateway restart mid-week interrupts live trading work; reconciliation makes it safe, but quiet is better. | P6-T5 | Proposed |
| D12 | Regions | Start with **one EU region** close to the customers and to the MetaApi region the brokers use; add US/Asia when demand exists. | Latency to MetaApi matters more than latency to the browser. | P3-T2 | Proposed |

## Signup (owner decision of 2026-11-25)

| D46 | How customers sign up at launch | **Normal registration on the website, then approval by staff.** A visitor creates an account (name, email, password, country, language, acceptance of the terms and the risk disclosure). | D47 | Where a new customer server gets Lonora | **It builds Lonora itself from the public repository** at `LONORA_VERSION` (a pinned commit), with the stock `build-from-source.sh`, then installs that image by digest. No published image is needed. | Owner: GitHub billing cannot be fixed, so do not rely on GitHub Actions. The repository is public, so the server needs no token. A build adds about 15-30 minutes to activation. | PW-T6 | Confirmed (2026-11-26) |
| D48 | Where Lonora Cloud runs | **One Hostinger KVM 4 server** (4 vCPU, 16 GB, 200 GB NVMe) holds the website, the admin panel, the build of each release and every customer's installation. Shared on the host: the reverse proxy, the search engine and one PostgreSQL server with a separate database and role per customer. Per customer: Lonora's server and worker, its own encryption key, its workspace and browser, started on demand with 1 GB. About six customers comfortably, eight at most; then the server is upgraded to KVM 8 in place. Staff activate from the admin panel (D46) in under a minute; each release is built once and every customer is switched in seconds. No Cloudflare and no server per customer; this replaces D47's build on every server and PW-T6's Hetzner and Cloudflare provisioning. Real memory use is measured on the server before the first customer. | Owner: «عند تحديث lonora و تفعيل مستخدم لا تاخذ اكثر من دقيقه», «سيرفر واحد بدل ان يكون اكثر من مكان مثل كلودفلير», «لمدة سنة كامل لو اخذنا خادم خاص بنا و كل عميل جديد نضيفه الى الخادم», «KVM 4 الا تكفي لي 8 عملاء», «نعم موافق».
