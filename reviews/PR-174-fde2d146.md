## Verified findings

### M1 (medium, 7.2/12.1): a rotated key can be paired with the old URL — the "one read" is two
- `packages/providers/src/lonora_providers/credentials.py:33-38` `connection`: the `{secret_id, url}` record is read in one session (`saved_key`). The session closes, then `self.store.read(saved.secret_id)` decrypts in a new one.
- A rotation card upserts the same `SecretRow`: same id, new value.
- Reproduced (fresh `_test` DB): card 1 saves `sk-old…` with `https://old.example/v1`; card 2 commits `sk-new…` with `https://new.example/v1` between the two reads. `connection("openai_compatible")` returns `('sk-new-key-2222', 'https://old.example/v1')`, so the new key goes to the address the owner just replaced. Commit 77439037's docstring says this cannot happen.
- One session is not enough under READ COMMITTED.
- Fix: read the setting, `SELECT … FOR SHARE` the `SecretRow` and decrypt, re-read the setting, and use the pair only if `secret_id`/`url` are unchanged (retry otherwise). Or run the whole read in a REPEATABLE READ transaction. Add a test that commits a rotation between the reads.

### L1 (low): Compose container-name spellings pass the endpoint check
- `packages/security/src/lonora_security/network.py:737-741, 758-776`: `LONORA_SERVICES` lists service names only. Docker DNS also resolves container names `${LONORA_PROJECT:-lonora}-<service>-<n>`, and one-label names are accepted over plain http.
- Reproduced: `compatible_endpoint` accepts `http://lonora-api-1/`, `http://lonora-db-1:5432/v1` and `http://lonora-gateway-1/`, while it refuses `api`, `db` and `gateway`.
- Impact is limited (the owner types the URL; only GET `/models` with the key).
- Fix: also refuse one-label names matching `^[a-z0-9-]+[-_](api|db|gateway|caddy|migrate|searxng|browser|workspace|workspace-net)[-_]\d+$`, or document the limit beside the "a name is not resolved" note.
