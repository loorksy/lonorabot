## Verified findings

### M1 (medium, 0.4): the "refused token" wake is false for a first account
- `packages/db/src/lonora_db/secret_cards.py:~168-170`: "The saved MetaApi API token itself was refused: ask the owner for a new one with broker_manage (action replace_token), never in chat."
- On `broker_token_rejected`, `_forget` calls `delete_unused(token_id)`. With no connection yet (the usual first connect), the token is deleted. Meanwhile `broker_manage` needs an existing connection's `account_id`, so `replace_token` cannot run. The next `broker_connect` card asks for the token anyway.
- Fix: branch on whether the token is still saved. If it is, keep the `replace_token` hint; if not, say "call broker_connect again; its card asks for the token".

### M2 (medium, safety of the owner's money): disconnect says nothing about open positions
- `broker_manage.disconnect` returns only `connection_id` and `removed_at_metaapi`. The tool description says only that an account Lonora created is removed at MetaApi.
- After disconnect, `prepare_delete` revokes grants and cancels approvals, the row is deleted and the Lonora-made MetaApi account is removed. Open positions and orders stay at the broker, and no agent reads or manages them any more.
- `set_enabled(False)` says this explicitly (its Q9 note); the irreversible action does not. It runs on any owner-typed run without a card.
- Fix:
  - add the note to the disconnect result and the tool description: "its open positions stay at the broker and are no longer read or managed";
  - include the count of open positions and pending orders read just before removal, so the agent states it to the owner in one line.

### M3 (medium, 7.2.3): disconnect deletes broker secrets through the general store, outside the provisioning lock
- `packages/trading/src/lonora_trading/broker_manage.py:129`: `await store.delete(secret_id)`, where `store` is the general `EncryptedSecretStore`.
- Its `delete` (`secret_store.py:104`) has no scope check, contradicting its own docstring (`:36` "… refuses them") and the rule that broker values go only through `BrokerSecrets`. It also skips the provisioning lock that `BrokerSecrets.delete_unused` takes since #141's L5 fix.
- Fix:
  - delete through `BrokerSecrets.delete_unused` (or a `BrokerSecrets.delete` under the same lock) and drop the `store` parameter;
  - add the broker refusal to `EncryptedSecretStore.delete`, so the docstring is true (the `DELETE /secrets/{id}` route then also refuses broker rows, which is consistent with 7.2.3).

### L1 (low, 17): the replacement card's token field says "(asked once)"
- `brokerToken` reads "MetaApi API token (asked once)" / «(يُطلب مرة واحدة)» on a `replace_token` card. Use its own label in both languages.

### L2 (low): a failure after MetaApi accepted the new password is reported as "Nothing changed"
- In `rotate_password`, if `credentials_changed` or the commit fails after `update_password` succeeded, the new password is deleted and the wake says nothing changed. The identity pre-check makes this unlikely.
- Fix: treat any failure after `update_password` as partial and say so.

### L3 (low): the connect-card subject changed format
- `secret:broker:<server>:<login>` became `secret:broker:connect:<server>:<login>`. A connect card in flight across the deploy no longer matches `other_card_active`.
- Fix: match both forms for one release.

### L4 (low): a connection created during `replace_token` can be missed
- The re-read of connections happens before `credentials_changed` takes `lock_owner`, and `_connect` takes `lock_owner`, not the provisioning lock. A connection committed in that gap silently gets the new, unchecked token.
- Fix: take `lock_owner` before the re-read.

## What I checked
- **Unknown outcomes:** disable, disconnect and rotate are refused while a `reserved`, `submitted` or `ambiguous` row exists. The probe inserted real journal rows; MetaApi was never touched. `rotate_password` re-checks under the send lock.
- **Ordering:** disconnect runs `prepare_delete` and the row delete under the send lock before any MetaApi undeploy or remove. The probe held the send lock as the door does: the waiting disconnect was refused after the operation ended ambiguous. An account the owner linked by id is never removed.
- **Lock order:** door, reconciliation and recovery take only the send lock (or try-lock). Manage takes send, then provisioning, then owner row, then broker row; connect takes provisioning then owner, or owner alone. There is no cycle, and a 60 s race probe saw no deadlock.
- **Stale credentials:** `credentials_changed` bumps the version, which the door's fence and the `BrokerManager` cache both see. Rotation holds the send lock across update and redeploy, so no half-rotated send happens.
- **9.3:** rotation goes through `provisioning.update_password` and `redeploy`. `.update(` appears only in the enable/disable path.
- **Secrets:** new values arrive only on server-fixed broker cards. The pending token is held as `metaapi_token_next:<card>` and replaces the saved one only after every connected account accepts it. Logs carry type names only, and no value appears in wake or result text.
- **Owner gate:** every action requires `owner_message_id`, with the 6.10 taint; routine and peer wakes are refused (tested).
- **Docs and cards:** the manifest check passes; card titles have Arabic and English and no raw ids.
- **Tests:** tests/test_broker_*, test_preflight_identity, test_tool_execution_core and test_financial_admission give 120 passed on a fresh DB. check_broker_recovery, check_account_recovery and check_broker_connection_uniqueness pass.
