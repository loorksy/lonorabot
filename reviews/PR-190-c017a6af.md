## Verified findings

### M1 (medium, 7.2.6): the start of a long secret in a command line is stored and shown
- `packages/workspace/src/lonora_workspace/supervisor.py:196` reads `cmdline` cut at 4096 bytes.
- `client.py:205-206` `processes()` applies only `scan.data(...)`. Unlike `run()`, it does not first replace a trailing partial secret with `trailing(scan, ...)`.
- A secret of about 3.8 KB or more (a PEM key, a JSON credential) passed as an argument and running past byte 4096 is not matched whole, so its start survives the scan.
- `Gateway.record_running` then keeps the first 300 characters in `ln_workspace_running`, and the owner's view shows them.
- Reproduced through the real `WorkspaceClient` and `Gateway.record_running` (secret = `-----BEGIN KEY-----` + 4300×Q):
  `SHOWN: curl -d -----BEGIN KEY-----QQQQ…QQQ` (273 secret characters stored and shown).
- The same `processes()` answer also reaches the agent through the process-listing tool, which predates this PR. The fix below closes both paths.
- Fix: in `processes()`, for each process run `item["command"] = trailing(scan, item["command"])` before `scan.data`, as `run()` does. Better still, have the supervisor say when it cut a command line and apply `trailing` then. Add this case to `test_workspace_running.py`.

### L1 (low): `tests/test_workspace_running.py` fails without PostgreSQL instead of skipping
- Without `LONORA_TASK_TEST_DATABASE_URL`, the `task_db` fixture falls back to SQLite, and the tests fail with `can't compare offset-naive and offset-aware datetimes` at `workspace_running.py:53/58`. Reproduced: 5 failed. With PostgreSQL, 5 pass.
- Fix: skip without PostgreSQL, as `test_card_lifetimes.py` does, or compare aware datetimes.

### L2 (low): an out-of-range pid gives a 500
- `apps/api/src/lonora_api/routes/workspace_running.py:19` has `pid: int = Field(ge=1)` but the column is `Integer`. Reproduced: `request_stop(..., 2**31, agent)` raises `DBAPIError`, which the route returns as a 500.
- Fix: `Field(ge=1, le=4194304)` (Linux's pid maximum) or `le=2**31 - 1`.

### L3 (low, 0.4/17): "Nothing is running" when the workspace has never answered
- With no listing row, the API returns `listed_at: null, stale: true`. Web (`RunningPage.tsx:89-104`) and mobile (`running.tsx:100-114`) show the stale note only when `listed_at` is set, and otherwise show "Nothing is running in the workspace." That is untrue when the workspace has not answered yet.
- Fix: when `stale` and `listed_at` is null, show a "the workspace has not answered yet" line instead of the empty-state text.

## What I checked (with a subagent; every item above verified by me)
- **Authorization:**
  - Both routes use `require_owner`, and a foreign `agent_id` gets 404.
  - The supervisor's stop requires the pid's uid to be that agent's user (`supervisor.py:633-640`).
  - Stop-all is sent per owned agent and never with no agent.
- **At most once:** claims use `UPDATE … WHERE done_at IS NULL … RETURNING`. A probe with two concurrent claimers on PostgreSQL got 20 claims, 0 doubled.
- **Scan:** the owner's full scan (stored values plus `ln_workspace_given`) is applied before the 300-character cut (except M1). Logs carry only failure codes.
- **Listing:** an older listing never replaces a newer one (`FOR UPDATE`, `listed_at` of the request). A listing older than 60 s refuses stops with 503, and the UI disables the buttons.
- **Migration:** 0139 is in the W-WS range and chains to 0136, with one head. Upgrade, downgrade -1 and upgrade work.
- **P5 and the views:**
  - "What is running" is a view P5 allows (7.1.5); Amendment 1 removes the trading Stop, not this process stop.
  - No pid or id is shown; commands are isolated left to right.
  - Web and mobile change together (14.1.4), with Playwright specs on a real PostgreSQL fixture (`tests/workspace_running_browser.py`).
- **Arabic:** all 12 web msgids have Arabic, with no empty msgstr; all 12 mobile `running_*` labels have Arabic.
- **Tests:** test_workspace_running gives 5 passed on PostgreSQL; shell-routes gives 6 passed; tsc for web and mobile, biome and ruff are clean.

## Rejected findings
- Stops are marked done when claimed, so a supervisor error drops the rest of the batch. This is documented ("a stop lost to a crash is tapped again") and is only a cost of at-most-once.
- No API-level test of the routes: the Playwright specs drive them end to end through the real API and PostgreSQL.
- "CI never runs the new pytest file": CI runs a fixed list (`run_foundation_checks.py`) and runs most test files of the repository the same way, so this is not specific to this PR.
