## Findings

### H1. A pause made in a run that read third-party content is stored as the owner's (6.10, 4.7.2, 3.1.2)
- `packages/tools/src/lonora_tools/supervision.py:467` passes `owner_words_id` from `owner_typed_message` with no taint check.
- `packages/db/src/lonora_db/supervision.py:528`, `:549-561` and `:593-594` turn it into `source='owner'` with `source_message_id` set.
- How it goes wrong:
  1. The owner asks Lonora to summarise a web page. The run is marked as having read external content, so `owner_message_id` is None.
  2. Lonora, steered by injected text, pauses Gold.
  3. The hold is stored as the owner's. The card says "from your message" and "This pause is yours: only you resume it" (`owner_actions.py:1033`), which is false provenance.
  4. Lonora can never lift that pause (`supervision_resume_not_yours`).
- So third-party or peer text can lock team agents into owner-only pauses carrying the owner's name. The "already paused" upgrade path does the same to an agent's self-pause.
- This contradicts `docs/agents-from-chat.md:57`: the owner's word counts only while the run has read nothing someone else wrote.
- Reproduced by me: `run.sh pr125 python -m pytest -q -s /home/user/wt/probes/pr125/test_probe_pr125.py` printed:
  - `owner_message_id after taint: None`
  - `tainted pause stored as: owner source_message_id set: True`
  - `Lonora resuming the pause it made (own judgment) -> supervision_resume_not_yours`
- Fix:
  - Drop `owner_words_id`: the parameter, the tool argument, and the `owner_typed_message`/`OWNER_TRIGGERS` use.
  - Use only the untainted `owner_message_id` for `asked_by_owner`.
  - Remove the "after other content" cases from `test_a_pause_the_owner_asked_for_stays_the_owners`, and add a tainted-run test asserting `source='lonora'` (or the acting agent).

### M1. The owner can no longer resume through chat a pause they asked for in chat (4.7.2, P5); a regression
- Every chat pause is now stored as `source='owner'` (`supervision.py:593`). Both resume paths then refuse it, whatever the run's untainted `owner_message_id`:
  - `supervision.py:606` refuses any resume of a `source == "owner"` hold;
  - `pauses.py:176` (`refuse_held`) refuses it too.
- So the owner types "Pause Gold", later types "Resume Gold now", and Lonora gets `supervision_resume_not_yours`. A direct resume through the agent gets `work_paused_by_owner`.
- The owner's untainted typed message is the mandate's sign of the owner's intent (3.3.4, 10.3.2, 14.3.5). 10.3.2 deletes the supervision cards, so chat is the owner's way to lift a pause.
- Reproduced by me with the same probe, `-k chat`: the PR head refuses with `supervision_resume_not_yours`; on base pr99 (ed12e7d7) the resume goes through.
- Fix:
  - In the `control_work` resume: when `hold.source == "owner"` and the run carries an untainted `owner_message_id`, release the hold as the owner's (`release_hold(hold, "owner")` or `owner_takes_over(..., paused=False)`) and apply the resume.
  - Do the same in `refuse_held` when `owner_message` is set.
  - Test: chat pause, then chat resume.

### L1. `lonora.md:471` is untrue for non-Lonora supervisors (0.4)
- The shared manual says "Resume lifts only a pause you made on your own".
- `supervision.py:609-611` still lets a non-Lonora supervisor, in an owner-message run, lift another supervisor's hold, Lonora's included. The PR body admits this ("Team agents keep one lift"). Confirmed by reading the code.
- Fix, either:
  - reword the line (Lonora lifts only its own; a non-Lonora supervisor with the owner's message also lifts another supervisor's); or
  - narrow the code so every supervisor lifts only its own (3.3.1).
