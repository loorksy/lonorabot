## Verified findings

### M1 (medium, 11.4; high if 11.4 is read strictly): pushes stop 24 hours after sign-in in a default deployment
- `packages/db/src/lonora_db/push_devices.py` `live_devices` (lines 99-107) targets only phones whose session has `expires_at > utcnow()`, and `prune_signed_out` (lines 124-130, called from `gateway/push.py:178`) deletes the expired ones.
- `issue_session` sets an absolute `expires_at = utcnow() + duration`, with `session_seconds` defaulting to 86400, and `read_session` never extends it. So a phone stops receiving pushes 24 h after it signed in, however often the app is used, until the owner signs in again.
- That is exactly when 11.4 needs it: "Reaching the owner when the app is closed is required".
- `docs/operations.md:483` "… to keep a phone reachable for longer without opening the app" implies that opening the app extends reach. It does not, and the setting is shared with web cookie sessions.
- Fix (the lead's choice):
  - (a) target phones whose session is not revoked, ignoring expiry (logout already deletes rows and revocation still prunes), with a long upper bound if wanted;
  - (b) or give mobile bearer sessions a long or sliding lifetime.
  - Correct the doc sentence either way.

### M2 (medium, 11.4): a push that never reached Expo is never retried
- `gateway/push.py:229-230`: `except Exception:` → `{"status": "ambiguous"}`.
- `adapters/channels/expo_push.py:37-38`: every 4xx, 429 included, becomes `push_request_refused` → `rejected`.
- Both are final, and the receipt key blocks a resend. A connect error, a DNS failure, a connect timeout, a 429 or a 503 means Expo accepted nothing, yet those pushes are lost with only a warning log.
- "Never resend an unknown outcome" is a rule for broker orders (6.3). For a push, a duplicate is low harm and a lost push defeats 11.4.
- Fix: classify not-delivered errors (`ConnectError`, `ConnectTimeout`, 429, 5xx) as retryable, with a bounded attempt count and backoff. Keep `ambiguous` only for a read timeout after the request was sent.

### L1 (low): 9.4 broker health could already push
- `PUSH_RECORDS` (`push.py:51`) covers `approval_required` and `operation_uncertain`, the two kinds the PR claims (0.4 holds). The Secret card, the proposed Mandate card and broker health are deferred to step 2b.
- Main already has the attention code `broker_degraded`, with a mandatory check and Arabic text.
- Fix: add it now (record = account id + `broker_recovery.since`, one push per problem), or keep the deferral recorded for the lead.

### L2 (low): no Expo receipts polling
- Only a ticket-level `DeviceNotRegistered` removes a phone. FCM/APNs invalidations usually arrive in `getReceipts`, so with M1 (a) dead tokens would persist indefinitely.
- Fix: poll `/--/api/v2/push/getReceipts` for the stored ticket ids and apply the same token-hash-guarded delete.

### L3 (low): `/ready` is unauthenticated and now tells whether push is configured
- `apps/api/src/lonora_api/health.py` returns `"push": "configured" | "not_configured"`. It is minor; drop it, or keep it if intended.

## What I checked
- **Idempotency:**
  - receipt `push:sha256(code, record, install id)` is committed with the cursor before any network call;
  - a per-owner advisory lock and a fresh cursor read make two gateways safe (tested);
  - the cursor is ordered and does not skip late commits;
  - the first run starts at the end of the stream.
- **Secrets:**
  - the device token is decrypted only in `live_devices`, sent only in the HTTPS body, and never logged;
  - the Expo access token is a `SecretStr`, sent only as Bearer to `https://exp.host` with `follow_redirects=False`.
- **Payload:** the agent's name (or "Lonora") plus fixed catalog text in the owner's locale (Arabic and English sets identical), and only `thread_id`/`around` as data. No price, symbol, account or secret, and no action button (6.10).
- **No extra push kinds:** receipts, reports and messages never push (tested).
- **Mobile tap:** opens the existing `/thread` route (P5); the launch response is cleared, so there is no stale replay.
- **Gateway step:** non-critical; at most 4 sends per tick, each bounded at 20 s; a row that cannot be decrypted is skipped.
- **Tests:** tests/test_push_sender.py and tests/test_push_devices.py gave 25 passed, and tests/check_durable_records.py passes, on a fresh PostgreSQL DB.
