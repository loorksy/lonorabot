## Verified findings

### M1 (medium, 6.10 provenance): a message forwarded to the bot becomes the owner's typed words
- Before this PR, a Telegram channel had no `allowed_destinations`, so inbound messages never reached an agent. Pairing (`telegram_pairing.py:69`) now sets them, which makes `event_dispatch.py`'s inbound path live.
- Any `message.text` from the paired chat goes to `send_message(... MessageCreate(content=...))` with the default origin `owner` (`messages.py:67`). `owner_typed_message` / `owner_message_id` then accept it, which unlocks every tool gated on the owner's own words: agent creation and control, owner profile and reach-me, model assignment, lifting a hold.
- Nothing checks `forward_origin`, `forward_from`, `forward_from_chat`, `forward_sender_name` or `via_bot` (grep "forward" over channels and gateway finds nothing). So a channel post or a stranger's message that the owner forwards to the bot reaches the model as the owner's own instruction instead of data.
- Cards are safe: they are decided only by their endpoints.
- Fix: in `decode_update` (or before `send_message`), drop forwarded or via-bot updates, or deliver them marked as third-party data. Add a test.

### M2 (medium, 0.4): a doc is untrue at this commit
- `docs/gateway-reliability.md:131-132`: "`run_quarantined` and `operation_unresolved` need action and are mirrored to Telegram while still current."
- 0c6f3073 (`event_dispatch.py:160`) now sends Telegram only `PUSH_CODES`, so those two are never mirrored.
- Fix: "need action and appear in the attention view; Telegram carries only the 11.4 push events".

### M3 (medium, P5 and 0.4; the lead decides): pairing extends a settings screen outside conversations
- The new pairing block is at `apps/web/src/shell/settings/IntegrationsPage.tsx:712-777` (Settings → Integrations → Telegram), and `docs/operations.md:521` sends the owner there.
- P5 allows no settings screen outside conversations, and 0.4 says contradicting code "keeps working, and no change may extend it". Against that, 11.4 lets the owner enable Telegram and 13 asks to complete half-built features.
- Fix (preferred): pair from chat. A tool returns the one-time `/start` code in the agent's answer, or a Secret card takes the bot token and its result shows the code. Leave the old settings page unextended until its removal.

### L1 (low, 0.4 and 17): other text not updated

### L2 (low, test wiring)

## What I checked
- **Bot token:**
  - stored as an encrypted integration secret;
  - adapter errors become `LonoraError(...) from None`;
  - `send()` failures become a fixed `channel_delivery_unconfirmed` without logging;
  - the `httpx` logger is at WARNING, so the request URL carrying the token is not logged;
  - the pairing route never returns the token.
- **Pairing code:** 8 characters from `secrets.choice`, stored as SHA-256 and compared with `compare_digest`; 10-minute expiry, single use, private chats only, owner-only routes.
- **Content:** only `attention.ready` items in `PUSH_CODES`, still current. Text is "<agent>: " plus the Arabic or English catalog text, with no ids, prices or card values. No agent replies, receipts or reports.
- **Idempotency:** one receipt per record and destination, written with the cursor before the send. A new pairing starts at the end of the stream. Telegram and push are separate gateway steps.
- **Inbound:** polling only; only the paired chat id is accepted; `/start` never reaches an agent.
- **i18n:** all new strings have Arabic.
- **Tests:** tests/test_telegram_channel.py, test_push_sender.py and test_attention.py give 56 passed on PostgreSQL. check_attention passes.
