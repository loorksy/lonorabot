## Findings

### M1. The owner's creation-card Undo can deadlock against the task's own Run (lock order)
- **Where:** `apps/api/src/lonora_api/routes/owner_actions.py:827-837` (`undo_creation`).
- **Lock order in the Undo:**
  1. it takes `authority_lock`;
  2. it locks the agent row FOR UPDATE (`:828`);
  3. it calls `pause_agent` (`agent_creation.py:383-399`), which calls `end_management_task`, which locks the task's Runs.
- `pause_agent`'s own comment requires the opposite: "before the agent's row lock: the task's Runs are locked first, as their own work does". A tool transaction of the task's Run (Run, then FOR KEY SHARE on the agent) therefore deadlocks with the Undo. That pattern is the one `tests/check_management_task.py:449-479` models.
- **Reproduced:** by the subagent's probe, which copies `undo_creation`'s order against that tool transaction: `['tool failed: DBAPIError … deadlock detected', 'ok']`. I confirmed both lock orders by reading the code.
- **Whose code:** this code comes from #80. This PR's merge keeps it, and the PR body's "no path waits the other way" is untrue.
- **Fix:** in `undo_creation`, call `end_management_task(session, owner.id, agent_id)` right after `authority_lock` and before `session.get(AgentRow, …, with_for_update=True)`. The call is idempotent. Add the Undo case to `check_management_task`'s lock-order checks.

### L1. The new test cannot see the Runs it claims to check
- **Where:** `tests/test_pauses.py` (around `:955-965`) selects the task's Runs by `model_metadata["task_id"]`.
- **Problem:** `close_task` → `detach()` strips `task_id` from every Run that continues. The query therefore finds only the cancelled Runs, and its `"queued"` branch can never match. A detached `waiting_input` or `running` Run is never checked.
- Found by reading the code; not executed.
- **Fix:**
  - record the task's Run ids before the pause, and assert on those ids afterwards (cancelled, or detached and not claimable while paused);
  - put one Run into `waiting_input` or `running` first, so the detached case is exercised.

## What was checked
- **Every pause entry point ends the task.** The owner's switch (`update_agent`), the owner's Undo (`pause_agent`), and Lonora's and the owner's chat pause (`control_work`, after `authority_lock`). Repeat calls are idempotent.
- **Resume restarts the task only on allowed paths.** These are the owner's switch, `_apply` after the 4.7.2 refusal checks, and `owner_resumes`. `ensure_management_task` refuses an agent that is paused or not in Full.
- **Refused pause rolls back.** A refused pause rolls back the task end, because the whole tool call is one transaction (probe P1).
- **No deadlock between a pause and a Full tap.** Two sessions, 12 iterations, alternating pause paths against `set_trading_mode(full)`: no deadlock, and never a paused agent with a live task.
- **A Run sending when the task ends is detached** (no `task_execution_stopped`). `require_pause_allows` then refuses risk-increasing requests and lets risk-reducing ones through, under the authority lock (4.7.1, 6.9).
- **Restart.** Nothing resurrects the task; a recovered Run goes through the paused gates.
