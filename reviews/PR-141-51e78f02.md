## Verified findings

### H1 (high, money and safety core): the provisioning step holds the owner-row lock across MetaApi's create, which stops the execution door from journaling any order
- `packages/trading/src/lonora_trading/broker_provisioning.py:195-217`: `_provision` opens a transaction, calls `repository.lock_owner()` (`SELECT … FROM ln_owners … FOR UPDATE`, `broker_sessions.py:117-124`), then awaits `provisioning.find_or_create(...)` inside it. That is several list calls plus a create, at up to 60 s each, and up to 10 minutes on MetaApi's long-running create (the step timeout is 900 s).
- In PostgreSQL every INSERT into a table with a foreign key to `ln_owners` takes `FOR KEY SHARE` on the owner row, which conflicts with `FOR UPDATE`. That covers `ln_trading_journal` (the door reserves every operation there before it sends), `ln_events`, `ln_owner_actions`, `ln_attention`, `ln_sessions` and dozens more.
- Reproduced end to end: the real `maintain_broker_provisioning` ran with `find_or_create` delayed 5 s. A journal insert in that window failed: `JOURNAL INSERT DURING PROVISIONING -> DBAPIError … canceling statement due to lock timeout after 2.01 s`.
- So while MetaApi is slow, no order (including a risk-reducing close) can be journaled on any account, and cards, events and sign-ins stall. Lonora has a single owner, so this freezes the app for up to ~10 minutes.
- Fix: never hold the `ln_owners` row lock across a MetaApi call.
  - Serialize provisioning with a dedicated advisory lock (`pg_advisory_xact_lock(hashtextextended('broker-provision:'||owner, 0))`), also taken by `broker_connect` around `other_card_active`.
  - Or claim the card in a short transaction (`provisioning="creating"`) and call MetaApi with no transaction open; the stable `transaction-id` and `find()` already make a repeated create safe.
  - Keep `lock_owner` only around the DB-only `assert_unique`/`create` in `_connect`.
  - If a FOR UPDATE on `ln_owners` remains anywhere, use `with_for_update(no_key=True)`, which does not block FK inserts (probe: 3.04 s wait with FOR UPDATE, 0.04 s with FOR NO KEY UPDATE).
  - Add a test: a journal insert must not wait while `find_or_create` is in flight.

### H2 (high, secret in logs, 7.2.6): the owner's trading password can reach the provisioning warning log in partly redacted form
- #88's `MetaApiProvisioning._failure` → `safe_exception_message` (`packages/core/src/lonora_core/error_logging.py:20-22`) removes only the exact password string. This PR is the first to send the owner's real password through it.
- Reproduced in isolation:
  - a MetaApi error that echoes the password JSON-escaped (a password containing `"` or `\`) leaves the part after the escape: `{"password": [redacted]c\\12x"}`;
  - hex, base64 and URL-encoded copies are not redacted at all.
- The text goes to the `broker_provisioning_create_failed` warning log. It never reaches the card or the wake (only `failure.code` is stored).
- Fix: do not log the SDK message for the `create` and `update` stages (log the code and status only). Otherwise also redact `json.dumps(v)[1:-1]` plus the base64, hex and URL-encoded forms of each secret.

### M1 (medium, 9.2/9.4): a rejected token that a connection still uses is a dead end
- On `broker_token_rejected`, `_forget` (`broker_provisioning.py:378-386`) calls `delete_unused(token_id)`.
- When a live connection still names the token (the one 0145 renamed, or one saved by an earlier connect), `secret_in_use` keeps it. The next `broker_connect` then asks only for the password (`broker_connect.py:53-62`), and `save_values` skips any token typed on an older card (`secret_cards.py:91-94`).
- The wake tells the agent to retry with `broker_connect`, which fails the same way. Nothing at this commit replaces the token, which nudges the agent to ask for it in chat.
- Fix: after `broker_token_rejected`, have `broker_connect` ask for the token again and let `save_values` replace it in that case (bumping the version of the connections that name it). Or say in the wake text that the token cannot be replaced yet.

### M2 (medium): a card can stay in progress forever and the agent is never woken
- The deadline (`_late`) is checked only inside the `except LonoraError` branches. Any other exception is logged and retried every pass with no deadline (`broker_provisioning.py:85-91`). Examples: an SDK construction error in `provisioning_client`, a decrypt error from `secrets.read`, or the step's 900 s timeout cancelling a long create.
- The phase never reaches `failed`, and `other_card_active` then refuses every new connect of that account with `broker_connect_in_progress`.
- Fix: in `maintain_broker_provisioning`, when any exception escapes `advance` after `started_at + DEPLOY_DEADLINE + READ_DEADLINE`, end the card through `Failing` with a fixed code.

### L1 (low): a MetaApi account Lonora created can be left behind and billed
- `Failing` commits `failed` and the wake, then calls `provisioning.remove()`. A `LonoraError` there is only logged (`:166-170`), and a crash after the commit skips it.
- A crash after MetaApi created the account but before `_record(created=True)` makes the next pass `find` it with `created=False`, so a later failure never removes it.
- Fix: record `create_sent` before the call (treat a found account as created when it is set) and `cleanup_pending` after a failure, and retry removal on later passes.

### L2 (low, 17): the settled card text is untrue after a failure
- `core/owner-actions.ts` `settledLine` always shows `brokerSaved` ("…connecting the account and will report its balance"), even when `result.provisioning == "failed"`.
- `continue_after_card` returns None for a paused or deleted agent, so nobody reports, although the card promises it.
- Fix: an ar/en "could not connect" line for `failed`, and a fallback to Lonora when the requesting agent cannot be woken.

### L3 (low): a wrong password takes 15 minutes to report
- `_deploy` waits for the whole `DEPLOY_DEADLINE` instead of failing early on `connection_status == "DISCONNECTED_FROM_BROKER"` with a password error.

### L4 (low): the platform input is lower-case only
- `BrokerConnectInput.platform` uses the pattern `^mt[45]$`, so "MT5" from the agent is a schema refusal, while `platform_of` ignores case.
- Fix: accept it case-insensitively and normalize.

### L5 (low, rare race): `delete_unused` checks use without the serialization lock
- `BrokerSecrets.delete_unused` (`broker_secrets.py:44-53`) does not take the same lock as `_connect`, so a token could be deleted while another card's `_connect` creates a connection naming it.
- Fix: take the provisioning lock in `delete_unused`.

## What I checked
- **Secrets:**
  - card result, events, messages, wake text and logs (outside H2) carry no password or token (`no_value_anywhere`);
  - broker values are written only through `BrokerSecrets.write_in_session`;
  - the generic `secret` card is hard-wired to workspace, and only `broker_connect` raises a broker card with server-fixed fields;
  - the token is never overwritten (`save_values`, the `lock_owner_actions` lock and `UNIQUE(scope,name)`; tested).
- **Owner-message gate:** `broker_connect` uses `owner_message_id` and refuses routine or peer wakes and runs that read third-party content (tested).
- **Safety core:**
  - the connection uses MetaApi's observed identity matched against the typed login and server;
  - `assert_unique` runs;
  - provisioning never calls `execute`, and the adapter never deploys;
  - cleanup removes only `created=True` accounts and is phase-guarded.
- **Gateway:**
  - `supervise_step` runs each step as its own task, so the step itself starves no other step (the stall is the DB lock in H1);
  - phases are checked under the card row lock;
  - `_record` and `continue_after_card` share one transaction, so the agent is woken exactly once.
- **Migration 0145:** byte-identical to the version reviewed on #103; single head; seeded up/down behaves as documented.
- **Text (0.4, 17):** the `lonora.md` lines and the tool description describe built behavior, and the manifest check passes. All 5 new card labels are in Arabic and English, and the card shows only login, server and platform.
