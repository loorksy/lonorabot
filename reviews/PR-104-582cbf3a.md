## Status of the findings from 7f4aa761
- **H1** (late ClientHello): **fixed.** A MetaApi SNI after 1.4, 1.6 or 2 s is refused, and trickled bytes are cut at `PEEK_SECONDS`.
- **H2** (name not tied to the address): **mostly fixed.**
  - An allowed SNI to an address it does not resolve to gives `relay_address_mismatch`.
  - Lowercase `get`, a leading CRLF, h2c, raw bytes and SOCKS5 give `relay_protocol_refused`.
  - Remaining gaps are M1 and M2.
- **M1** (UDP): **fixed.** All agent UDP is rejected.
- **L1** (daemonized process survives the time limit): **fixed in code.** The commit stops double-forked daemons; not re-probed.
- **L2** (relay exhaustion): **fixed** per uid. The cap is 256 per uid (300 idle connections → 44 closed), and another uid still connects. The global cap is 2048.
- **L3** (IPv6): **fixed.** The rule is `meta nfproto ipv6 meta l4proto tcp`.

## A note for the lead
7.1.2 requires internet egress and SSH. Under those, no relay can fully meet 7.1.4's "MUST NOT reach any MetaApi host": a wildcard-DNS name (M3) or a tunnel through any cooperating server always works. The relay is a defense in depth; what really holds is 7.2.3 (no MetaApi token or broker secret ever enters the workspace). The findings below are rated with that in mind. The docs must say it plainly.

## Verified findings

### M1 (medium, 7.1.4): an IP-literal name passes as "bound"
- `relay.py:211-213` `bound`: when the name is an IP equal to the dialled address, it returns OK.
- Reproduced: TLS with `SNI=45.33.1.2` to 45.33.1.2, and HTTP with `Host: 45.33.1.2`, both reached the upstream. No DNS is needed, only the address.
- Fix: refuse IP-literal SNI (RFC 6066 forbids it) and IP-literal Host on TLS/HTTP to public addresses. Or list it as a known residual in the docs.

### M2 (medium, 7.1.4): a CNAME into MetaApi passes, because the relay's own lookup is not screened
- `netguard.py` `Answers.of` → `resolve([name])` → `dns.addresses(answer)` (~lines 112-122) takes every address in the chain. Unlike the agent-facing forwarder path, it never applies `screened()`/`name_denied` to the CNAME chain.
- Reproduced end to end: the agent's own lookup of `evil-cname.example` (CNAME `mt-client-api-v1.new-york.agiliumtrade.ai`, A 45.33.1.2) returns NXDOMAIN. But TLS to 45.33.1.2 with `SNI=evil-cname.example` completed the handshake and got `HTTP/1.0 200 ok`.
- Fix: in `Answers.of`, discard an answer whose chain names a denied domain. Also keep every address learned through a denied chain on the blocked set.

### M3 (medium, 0.4): the docs overclaim what the relay stops
- `docs/operations.md` (English, and the Arabic summary at line 31) and `relay.py:8-9` say a hard-coded MetaApi address behind another name, DNS-over-HTTPS or a public proxy does not reach MetaApi. That is false at this commit:
  - IP literals and CNAMEs pass (M1, M2);
  - wildcard-DNS names pass (`SNI=45-33-1-2.sslip.io` completed a handshake with the unlearned address and got HTTP 200; no registration needed);
  - a public HTTPS proxy (TLS to the proxy, CONNECT inside) is invisible;
  - any byte stream after an `SSH-` prefix passes (`SSH-2.0-x\r\n` followed by a SOCKS5 greeting reached the upstream), so any tunnel through a cooperating server works, encrypted or not.
- Fix: in both languages, say the relay refuses MetaApi names it can see, and that any MetaApi server answering a foreign name, a wildcard-DNS name, or any proxy or tunnel through a server the agent controls still gets through. What holds is that no MetaApi token or broker secret enters the workspace (7.2.3).

### M4 (medium, 7.1.2 long-running work): the idle timeout is per direction, so long one-way transfers are cut
- `relay.py:185-191` `pipe()` wraps each direction's read in `wait_for(..., IDLE_SECONDS)`, and a timeout closes both streams.
- Reproduced with `IDLE_SECONDS=3`: a server streamed one chunk per second while the client stayed silent, and the connection was closed after 3.0 s with 3 of 10 chunks received.
- With the real 3600 s, any download or stream where the client sends nothing for an hour is cut while data flows: a large pip or model download, a long git clone, server-sent events.
- Fix: one shared last-activity timestamp per connection, checked by a watchdog.

### L1 (low, availability): the answer cache can be driven into an O(n) rebuild per query
- `Answers.record` rebuilds the dict on every insert once it holds more than 20000 names, dropping only expired (900 s) entries.
- Reproduced: 20000 unique wildcard queries took 6.0 s; the next 20000 took 82.0 s on the single event loop shared by the forwarder and the relay. Guard RSS went from 26 to 44 MB (limit 192m).
- Fix: a bounded LRU (`OrderedDict.popitem(last=False)`) and a per-uid query rate limit.

## Rejected
- Keep-alive requests are not re-inspected: a later request on a connection whose first Host was bound to that address reaches the same address. That is equivalent to M3's residual, not a separate gap.
- The relay opens TCP to the destination before a quiet client has spoken: no data passes uninspected.

## False positives (local stand-ins; low, for awareness)
- **Pass:** TLS with an allowed SNI to its own address (pip, npm, git over https) and a websocket Upgrade.
- **Refused:**
  - `git://` (pkt-line, client-first);
  - HTTP/1.0 without Host;
  - WebDAV `PROPFIND` (not in `HTTP_METHODS`);
  - `curl https://<ip>` without SNI.
- Consider adding `git://` and the WebDAV methods to the allowed client-first set.
