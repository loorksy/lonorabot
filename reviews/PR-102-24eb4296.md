## Rebase request
`git merge-tree origin/main 24eb4296` conflicts in `infra/compose/lonora`: main merged #68, which removed the
`goal_exits` part of `control_fingerprint`. On rebase, `lonora-controls.sh` must not re-add `goal_exits`
(`ln_trading_goals` is dropped by `0068_end_trading_goals` on main, so the part is always `absent`: a dead reference

## Findings

### M1 (medium) — the update that first delivers this file still runs the installation's old fingerprint; the "unblocks table drops" claim does not hold for installations whose `lonora` predates it
- `infra/compose/lonora` has no self re-exec: `install_bundle` (lonora:525-543) replaces files by rename, and the
  running bash keeps executing the old script; `cmd_update` never re-runs the newly installed copy.
- So the first `lonora update` into a release carrying `lonora-controls.sh` computes the baseline (and any rollback
  comparison) with the installed script's inline `control_fingerprint`. A pre-#68 installation (e.g. lonora at
  2a244c8c) reads `ln_trading_goals` unguarded (removed lines in this diff: `... FROM ln_trading_goals t WHERE ...`);
  after `0068_end_trading_goals` drops the table the baseline is empty → `fail_update 'reading the owner-control
  records'` → `rollback` reads `now` with the same old definition → empty → **ROLLBACK HELD**, needing `--force`.
- Nothing in `docs/operations.md` tells the operator about this one-time transition.
- Fix: document the one-time step in `docs/operations.md` ("an installation whose `infra/compose/lonora` has no
  `lonora-controls.sh` next to it: first install the target bundle's script, e.g.
  `docker run --rm --entrypoint cat <image> /app/deploy/infra/compose/lonora > infra/compose/lonora` and the same for
  `lonora-controls.sh`, then run `sudo lonora update`"), and/or make `cmd_update` self-upgrade before any state
  change: read the target's `/app/deploy/infra/compose/lonora`; if it differs from `$SELF`, install it and
  `exec "$SELF" update "$@"` with a guard variable (helps every later transition of the script itself).

### L1 (low) — `task_exits` reads keys that do not exist; the doc claims it covers tasks
- `lonora-controls.sh` `task_exits` reads `t.state->>'status'` / `t.state->>'control_requested'`, but a task's state
  lives under `state->'task'` (`packages/db/src/lonora_db/tasks.py:74-75,90`: `row.state["task"]`).
- Probe on a migrated DB (r102_test): ticket `state={"task":{"status":"running"}}` → fingerprint `6abcb738…`; set
  `state={"task":{"status":"cancelled","control_requested":"cancel"}}` → fingerprint `6abcb738…` (unchanged).
- Practical impact is limited: the owner's own pause/cancel of a task goes through `owner_takes_over`
  (tasks.py:417) and writes an `ln_supervision_holds` row, which this PR adds to the fingerprint. But the part is
  dead and `docs/operations.md` now says it covers "paused or cancelled … tasks".
- Fix: `t.id || ':' || coalesce(t.state->'task'->>'control_requested','') || ':' || CASE WHEN t.state->'task'->>'status' IN ('paused','cancelled') THEN t.state->'task'->>'status' ELSE '' END`
  with the matching WHERE, plus a parametrized test case using the nested shape.

## Rejected (one line each)
- "Rollback could use a different definition than the baseline": no — both go through `use_controls` with `state/update-controls.sh`, kept/held/restored with the marker (lonora:578-584, 763, 772).
- "An unguarded part remains": no — every part goes through `control_part`, which checks `to_regclass` first.
- "Owner routine/watch pause or watch cancel escapes the fingerprint": no — `configure`/`control_watch` call `owner_takes_over`, which writes `ln_supervision_holds` (now covered).
- "Sourcing image content into the root host script widens trust": no — the update already installs and runs the image's own `lonora`.
- "A held update from a pre-#102 script then rolled back with the new script always holds": true but fail-safe (hold, never a wrong restore); covered by M1's documentation.
