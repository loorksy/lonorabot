## Verified findings

### L1 (low): two concurrent registrations of one Expo token give a 409
- `packages/db/src/lonora_db/push_devices.py`: a select-then-insert under the session's row lock only. Two sessions registering the same token race on `UNIQUE(token_hash)`.
- Probe on PostgreSQL, two sessions PUT the same token 10 times each:
  - different install ids: one request got 409 `resource_conflict` in 10/10 runs;
  - same install id: 8/10 runs.
- No 500s, and the app retries on the next foreground, so this is low.
- Fix: `INSERT … ON CONFLICT (token_hash) DO UPDATE` (rebinding to the caller's session and install), or retry once on `IntegrityError`.

## Notes for W-PUSH 2 (not findings at this commit)
- Only an explicit `POST /auth/logout` removes a device row. `ON DELETE CASCADE` on `session_hash` never fires, because sessions are only marked `revoked`, never deleted.
  - A mobile session expires after `session_seconds` (86400 by default), and the app signs out locally without a server call. The same happens when the logout POST fails offline.
  - In both cases the row stays bound to a dead session. The sender must decide whether such a phone still gets pushes (11.4 "reaching the owner when the app is closed") or not, and the docs must then say which.
- Plausible, not reproduced: `apps/mobile/scripts/android-release.py:65` resolves `LONORA_ANDROID_GOOGLE_SERVICES_FILE` to an absolute path, but `scripts/ota-publish.sh` uses it as given. With `runtimeVersion: {policy: "fingerprint"}`, a differently spelled path may yield a different runtime, so an update would not reach the push APK. Resolving it with `realpath` in `ota-publish.sh` is cheap.
