## Verified finding

### L1 (low): a lost code message blocks the chat for ten minutes, and the comment says otherwise
- `packages/gateway/src/lonora_gateway/event_dispatch.py:147-153` sends the offer after the transaction that stored the code. The comment says "Best effort: a lost answer costs the owner one more message to the bot".
- But `offer_code` (`telegram_pairing.py`) returns None while this chat's code still waits.
- Reproduced:
  ```
  offer_code(row,'111') -> code
  offer_code(row,'111') -> None   (the immediate retry after a lost send)
  ```
- So after a failed send, the owner's next messages get no code for up to `PAIRING_LIFETIME` (10 minutes). The comment is untrue at this commit (0.4).
- Fix: either drop the waiting code when its send fails (a second short transaction removing that `pending_chats` entry), or word the comment and `docs/operations.md` honestly ("a lost answer: write to the bot again after ten minutes").

## What I checked
- **Pairing:**
  - Codes come from 32 unambiguous characters, 8 long (`secrets.choice`). They are stored only as a SHA-256, last 10 minutes and work once.
  - Codes are offered only to private chats and never by a bot that already has a chat (no hijack). A chat gets one waiting code at a time, and at most 3 chats wait, the oldest evicted.
  - The words of an unpaired chat never reach an agent; forwarded messages still never do (6.10).
- **`telegram_link`:**
  - It links only when `owner_message_id` is set: an untainted owner-triggered run, the owner's own messages (`origin == "owner"`), at most 160 characters, with the code as a whole word.
  - It takes the lease lock and an effect receipt, so a replay answers as before.
  - `link_chat` locks the owner's Telegram rows `FOR UPDATE` and takes only an enabled, unpaired bot. Delivery starts at the end of the event stream, so there is no backlog.
- **Gateway:** the dispatcher reads destinations from the locked row, and offers use the owner's locale (Arabic default). The log line carries no chat id, code or token.
- **P5 and 14.1.4:**
  - The Settings pairing component and the `/telegram/pairing` and `/telegram` routes are removed together; no web or mobile caller is left.
  - `.po` files are regenerated, with Arabic present.
  - The tool has no label of its own, but the turn view falls back to its family label (`turn-activity.ts:324-330`), so no raw name is shown.
- **Manifest and docs:** the manifest is regenerated (5.8.6). `docs/operations.md` describes the chat flow (except L1).
- **Tests:** test_telegram_channel, test_context_engine, test_release_manifest and the telegram and integrations tests give 148 passed. ruff is clean.

## Rejected findings
- Strangers writing to an unpaired bot can evict the owner's waiting code (`MAX_WAITING=3`). This is by design and documented: the owner's next message gets a new code, and nobody can link without the owner typing the code.
