## Verified findings

### M1 (medium, 6.3/6.4): an order that may have been sent is reported to the owner as "connection unavailable"
- `packages/gateway/src/lonora_gateway/broker_relay.py:44-53`: `serve()` maps every non-`LonoraError` from `perform()`, including those from `services.trading.execute`, to `broker_connection_unavailable` (502).
- `ExecutionService.execute` can raise after the broker call returned (for example, a DB failure in `conclude()` writing the outcome).
- Reproduced on PostgreSQL with the real Gateway `ExecutionService` and a fake MetaApi terminal whose outcome write fails:
  ```
  broker sends: ['create_market_order']
  journal status: submitted
  owner sees: broker_connection_unavailable 502
  ```
- The owner text is "The broker connection is unavailable." («الاتصال بالوسيط غير متاح.»), which reads as "not sent" for an order that went out. An owner placing the order again creates a second position.
- The journal stays correct (`submitted`, reconciled later), so nothing is resent by Lonora.
- Fix: for `request.kind == "execute"`, answer any non-`LonoraError` with `broker_gateway_no_answer` (504), whose text already says to check trades before trying again. Better: return the journal's receipt for the order's operation id. Add a relay test that runs a real door execution through the relay (the PR's test mocks `trading.execute`).

### M2 (medium, the PR's own "the throttle outlives a restart"): a throttled account-metadata read is not carried
- `brokers/metaapi.py` `resolve_account` (~296-324) honours `recommendedRetryTime` inside the process, but raises a `LonoraError` without `retry_until` and never sets `_throttled_until`.
- `create()` (~445) calls `throttled_until(error)` on that already-wrapped error, which returns None.
- So `reconcile_broker_account` stores `throttled_until=None`, and a restarted Gateway asks MetaApi again before its time.
- Reproduced (get_account raising TooManyRequests with 600 s, then `prepare()` and `read_rpc()`): `code broker_rate_limited retry_until None`, `stored throttled_until None`, `adapter account_throttle None`.
- Fix: set `self._throttled_until` and `failure.retry_until` when `until` is known, also on the cached failure. In `create()`, read the time from `retry_until` or `__cause__`.

### M3 (medium, "every SDK call checks the throttle" / "never undercut"): a 429 on historical candles is retried at once
- `candles()` (~901-930) calls `get_historical_candles` without a retry time.
- Reproduced: three `candles()` calls inside MetaApi's 600 s window ask MetaApi three times.
- Fix: keep a REST cooldown from `throttled_until(error)` and check it at entry, as `_history_access` does. Keep it separate from the websocket throttle (check_broker_recovery requires that blocked synchronization does not block REST).

### M4 (medium, 0.4): `docs/attention.md` is untrue at this commit
- Line ~19: "Every item is `action_required`". But `SYSTEM_ATTENTION["broker_rate_limited"] = "important_change"` (`lonora_db/attention.py:50`).
- The flapping paragraph says a lost connection is replaced by the specific problem. For throttling, `mandatory_current` keeps whichever of lost or rate-limited came first.
- Fix: state both.

### L1 (low): slow reads can crowd out an owner's order
- `IN_FLIGHT = 16` (`gateway/broker_relay.py:26`), and `claim()` orders by `created_at` only (`db/broker_relay.py:128-150`). Reads may each take `READ_SECONDS`, and `/ws/market` polls quotes through the relay.
- With 16 slow reads in flight, an order waits past its 5 s claim window and is withdrawn. That is the safe direction (nothing reaches the broker), but the order fails for availability.
- Fix: claim `execute` first (`ORDER BY (kind <> 'execute'), created_at`) or reserve a slot.

### L2 (low): `ask()`'s docstring
- `db/broker_relay.py:58-60` says "an order is in the journal" for a claimed, unanswered request. A Gateway that crashed before reserving left nothing.
- Fix: "an order, if reserved, is in the journal".

### L3 (low): a stopped quote reads "stale" on a closed market or a quiet symbol
- `contracts/market_health.py` `as_of`: any healthy quote older than 2 minutes is `stale` / `market_quote_stale`, regardless of trading hours.
- Over a weekend every streamed symbol shows "Market data unavailable" in the agent live status (web and mobile). It is display only: no event, alert or push.
- Fix: use trading hours when known, or word it "no new prices since …".

### L4 (low, 17 / 14.1.4): owner text for `broker_rate_limited`
- Web `user_error.ts:161-162` still says "The broker market-data service is rate limited." The code now also covers throttled account, position and history reads.
- Mobile `i18n.ts` has no `broker_rate_limited`, `broker_gateway_unavailable` or `broker_gateway_no_answer` label, so the generic fallback shows (no raw code).
- Fix: widen the web text, and add ar/en mobile labels.

## For a decision (not a finding)
- An outage that starts as throttling stays an `important_change` item even if it later becomes a real lost connection lasting hours. `check_attention_items` asserts this on purpose; it may be worth letting `broker_connection_lost` replace it after the grace.

## What I checked (two subagents by dimension; the mediums reproduced or read by me)
- **Safety core (Section 6):**
  - One door: `broker.execute` has a single caller (`execution.py:500`). `RelayedBroker.execute` and `reconcile` raise `broker_send_in_gateway`.
  - The API hands the whole owner order to the Gateway, which runs the same `ExecutionService.execute`. The journal, operation id, reserve-before-send, fingerprint, preflight account match, stale target, permission and authority lock all run there.
  - An `execute` row whose account differs from its connection is refused.
- **Never resend:**
  - On PostgreSQL, 8 concurrent claimers over 40 orders claimed each exactly once (`FOR UPDATE SKIP LOCKED`). Neither claimed rows nor rows past their window are re-claimed.
  - Withdraw against claim: exactly one side won in 200 races.
  - Claimed and unanswered gives `broker_gateway_no_answer` (504), and the row is never re-claimed.
- **Secrets:** relay rows hold only the order or read arguments and results. They are deleted on read and pruned after 1 h. Logs record only kind and exception type, and no token reaches the throttle state.
- **Migration:** 0146 is in W-BROKER's range (0145-0149) and chains to `0087_end_money_limits`, with one head. Upgrade, downgrade and upgrade work, and the partial index fits the claim query. (W-WS's #228 moved off 0146 to 0200, so no collision remains.)
- **Throttling otherwise:** the SDK patch matches SDK 3.x, the synchronize pre-sleep honours MetaApi's time, there is no reconnect storm, and undeployed stand-down and recheck work.
- **Health and attention:** `broker_rate_limited` is classified in py and ts, with the grace, one item and push per outage, and Arabic and English in `attention_messages.json`, the web `.po` files and mobile.
- **Tests:**
  - The 14.1.2 core checks pass: check_trading, check_execution_recovery, check_broker_recovery, check_account_recovery and check_broker_orders; the six core pytest files give 101 passed.
  - test_broker_relay, test_metaapi_rate_limits, test_metaapi_undeployed, test_market_quote_staleness, test_attention, test_broker_* and test_metaapi_account_readiness pass. check_attention_items passes.
  - ruff check and ruff format are clean. Test diffs change with the feature, and none weakens an assertion.
