## Verified findings

### M1 (medium, 0.4 and 9.2): "one owner MetaApi token" is not built, but the code and text say it is
- `packages/db/src/lonora_db/secrets.py:20-21`: `# The owner's one MetaApi API token (scope broker); every MetaApi connection names it.` / `METAAPI_TOKEN = "metaapi_token"`.
- Grep: no runtime code reads or writes `METAAPI_TOKEN`. It appears only in the migration and tests.
- `packages/trading/src/lonora_trading/connections.py:98-99` still stores the token per account: `config.secret_id = await secrets.write_in_session(session, config.account_id, api_key)`. After 0145 renames the token, the next connection made with a key creates a second copy named after its account id. The owner still enters the token per connection, against 9.2 ("enters a MetaApi API token once").
- 0145's docstring ("Until now each MetaApi connection stored its own copy …") implies the copying stops; it does not.
- With two connections on different tokens, nothing is renamed. Seeded and run: the rows stayed `acct-1` and `acct-2`. So "every MetaApi connection names it" is false even for migrated data.
- Fix, one of:
  - **Build it here:** `connect_account` writes the value under `METAAPI_TOKEN` (upsert by name, scope broker) and reuses the stored token when the request carries no `api_key`. Then bump the version of the connections that name it, or evict `BrokerManager`'s cache (`adapters/brokers/base.py`, keyed by connection version), so running brokers do not keep the old token. Add a test that a second connection reuses the one token.
  - **Or keep it out of this PR:** drop the constant, its comment, the 0145 rename and the title claim until the provisioning connect flow lands.

### L1 (low): the boundary test guards by text and misses some read routes
- `tests/test_broker_secret_boundary.py:28-41` only searches for `"import BrokerSecrets"`, `"BrokerSecrets("` and `"class BrokerSecrets"`.
- It does not catch:
  - `SecretCipher(key).decrypt(row.ciphertext)` on a broker `SecretRow`, since `SecretCipher` is public in lonora_security;
  - reaching `context.brokers._secrets`, since `ToolContext` carries the `BrokerManager`.
- What really enforces the boundary is the runtime scope refusal in `EncryptedSecretStore.read` / `write_in_session` (verified sound).
- Fix: also guard `SecretCipher(` and `.decrypt(` outside the storage and security modules, and assert that no module outside the broker layer touches `_secrets` on a `BrokerManager`.
