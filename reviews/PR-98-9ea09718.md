## Finding 1 (medium): one outage whose reason flaps raises a new item and a new push on every flip

- Files: `packages/db/src/lonora_db/attention.py:807,817` (`follow_broker_health`) and `:128` (`mandatory_current` for broker codes).
- Evidence:
  - The item's identity is code plus outage start (`since`). When the reason changes within the same outage, `mandatory_current` turns False, `withdraw_ended` suppresses the item, and the next flip raises the code again under subject `account:since:<n>`.
  - `reconcile_broker_account` (`packages/trading/src/lonora_trading/broker_recovery.py:114-119`) keeps `since` for the whole disconnection but rewrites `reason_code` on every poll. A 401 gives credentials rejected, while a timeout or rate limit gives connection lost once the grace period has passed. A rejected-token or undeployed outage during MetaApi slowness therefore alternates codes.
  - Probe on a fresh database, using the PR's own `set_recovery` and `tick` helpers: one outage, 8 polls alternating `broker_credentials_rejected` and `broker_connection_timeout`, gave `items token=4 lost=4 attention.ready events=8`. That is eight pushes for one problem, against 11.4's one push per creation.
- Fix:
  - Within one outage (same account and `since`), keep an open `broker_token_rejected` or `broker_account_undeployed` item current while later polls show only a generic connection-lost reason.
  - In `follow_broker_health`, do not raise `broker_connection_lost` while an open item exists for the same account and `since`.
  - Re-raise within one outage only after re-enable, not on a reason change. Alternatively, key the subject per outage (`account:since`) independent of code.
  - Add a check case that alternates reasons and asserts a single `attention.ready`.
