## Verified findings

Test setup for H1-H3: two network namespaces, with the PR's own `egress.ruleset(['45.33.1.9'])`. 45.33.1.9 stands in for a learned MetaApi address and 45.33.1.2 for a MetaApi address that was not learned. The PR's `Relay` runs as root, and the probes run as uid/gid 20000.

### H1 (high, 7.1.4): a client that waits 1.5 s before its ClientHello is never inspected
- `packages/workspace/src/lonora_workspace/relay.py:191-196`: if the first bytes do not arrive within `FIRST_BYTES_SECONDS`, `name = ""` ("the server speaks first"). Line 207 then skips the name check, and every later client byte is piped unread.
- Reproduced: connect to an unlearned MetaApi address (another region or instance, resolved over DNS-over-HTTPS, or hard-coded), sleep 2 s, then run a normal TLS handshake with SNI `mt-client-api-v1.new-york.agiliumtrade.ai`. With `delay=0` it is refused; with `delay=2` the handshake succeeds and the request gets `HTTP/1.0 200 ok`. This works on any port.
- Fix: after the timeout, keep reading. If the client sends before the upstream has sent anything, run the same TLS/HTTP checks on those bytes. Pass through only when the upstream really spoke first, and refuse unknown client-first bytes.

### H2 (high, 7.1.4): the relay checks the name the client claims, then dials the original address
- `relay.py:188,209`: it dials `open_connection(host, port)` from `SO_ORIGINAL_DST`, and the checked name is never tied to that address.
- Reproduced against an unlearned "MetaApi" address:
  - TLS with SNI `example.com` reaches it;
  - HTTP keep-alive whose first request says `Host: example.com` and second `Host: <metaapi>` reaches it (the upstream log shows both requests);
  - a lowercase `get` with a MetaApi Host, or a leading CRLF before `GET` (valid per RFC 9112 §2.2), is treated as an "unknown protocol" and passed through;
  - h2c `PRI *` and raw bytes pass, so a plaintext SOCKS5 or HTTP proxy on the internet does too.
- Whether MetaApi's front end accepts a mismatched SNI/Host is unknown, but H1 does not depend on it.
- The docs overclaim (0.4):
  - `relay.py:10-11`: "a hard-coded MetaApi address, DNS-over-HTTPS or a public HTTP proxy does not reach MetaApi";
  - `docs/operations.md`: "so a hard-coded address or DNS-over-HTTPS does not help". The doc names only an encrypted tunnel as the exception.
- Fix:
  - dial the checked name (resolved through the guard's filtered forwarder) instead of the original address, or require the original address to be among that name's answers;
  - inspect every request on a kept-alive HTTP connection, or force `Connection: close`;
  - refuse unrecognised client-first protocols by default (allow-list SSH's `SSH-` banner and the other protocols you mean to pass);
  - until this holds, say in both languages that a hard-coded address with a different name, or any proxy, can still reach MetaApi.

### M1 (medium, docs 0.4): only UDP 443 is rejected
- `egress.py:105`: `meta skuid != 0 udp dport 443 reject`. Reproduced: UDP to port 8443 reached the upstream.
- So QUIC on another port, or a UDP VPN, leaves freely. The docs' "QUIC … rejected" is true only for port 443.
- Fix: reject agent UDP except to the forwarder (DNS) or to an allow-list. Otherwise reword the docs.

### L1 (low): a daemonizing program still outlives the foreground limit
- `supervisor.py` `descendants()` walks parent links. A double-fork daemon is reparented to init, so it is no longer a descendant.
- Reproduced with the real supervisor: `python3 -c 'fork; setsid; fork; exec sleep 76'` was still alive after a 2 s timeout (`5511 1 20000 … sleep 76`). Plain `setsid sleep 77` is now killed.
- The comment "every descendant that left it (setsid, daemonize)" is untrue for daemonize.
- Fix: tag each job, either with an env marker (for example `LONORA_JOB=<id>`, read from `/proc/*/environ` as root) or with a per-job cgroup, and kill everything carrying it. Otherwise drop "daemonize" from the comment.

### L2 (low, availability): one agent can exhaust the relay for all agents
- `Relay(limit=512)` is global, with no per-uid cap and no idle timeout. A connection that sends nothing goes to pass-through and holds its slot forever.
- Reproduced: 515 idle connections, after which another agent's connection got `ConnectionResetError(104)`. Only workspace networking is affected.
- Fix: a per-uid limit (an nft `ct count` per `skuid`, or tracking the uid of the peer) and an idle timeout.

### L3 (low, latent): the IPv6 TCP rule matches only packets without extension headers
- `egress.py:106`: `ip6 nexthdr tcp` misses a TCP packet with a routing header (`IPV6_RTHDR`). Moot today, since the compose network has no IPv6.
- Fix: `meta nfproto ipv6 meta l4proto tcp reject`.

## What I checked
- Every agent TCP port is redirected to the relay. A MetaApi SNI on 443, 8443 or 2222 is refused.
- Spelling variants are refused: uppercase with a trailing dot, a 1-byte-segmented ClientHello, absolute-URI, CONNECT, `Host :`, a hello without SNI.
- The learned MetaApi address is rejected, including for the relay's own dial. Private ranges and the Docker resolver stay rejected for the relay.
- A direct connection to the relay port is closed without a dial.
