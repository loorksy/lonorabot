## Verified findings

### M1 (medium): a workspace secret named like a provider key still becomes the router's key without a model card
- `packages/db/src/lonora_db/model_credentials.py:12-22`: `credential_id` takes the newest row of either `(scope provider, name=provider)` or `(scope workspace, name=PROVIDER_KEY_NAMES[provider])`, for example any workspace secret named `OPENAI_API_KEY`.
- `ProviderCredentials.resolve` prefers that row over the deployment's key.
- Commit 343c8df states the intent: "An agent's own Secret card could save a value under OPENAI_API_KEY and so set the router's key without the owner seeing a model card. Those names are now reserved." But the reservation is checked only when an agent proposes a card (`tools/owner_actions.py` ~182-184).
- These still set the router's key:
  - a workspace secret migrated by 0070 from per-agent secrets with such a name;
  - a generic Secret card proposed before the upgrade and confirmed after;
  - a key the owner gave a workspace script on purpose (for example a restricted project key).
- Fix: record what the `model_provider` card saved, for example a setting `model_key:<provider>` = secret id written in `connect()`, beside `model_endpoint:`. `credential_id` then reads that id or the provider-scope row, newest first, and never matches by workspace name alone.

### M2 (medium, 14.1.3): the new web assertions never run
- `tests/web/model-provider-card.test.ts` is not in the `tsx --test` list at `.github/workflows/ci.yml:829`. That list does name `secret-card.test.ts` and `capabilities.test.ts`, and `grep -rn model-provider-card` finds no runner.
- Fix: append `tests/web/model-provider-card.test.ts` to that line.

### L1 (low, 7.2.3/10.3 transparency): the agent chooses where the owner's key is sent, and the card's hint can read as the opposite
- For `openai_compatible` the agent supplies `url` (`apps/api/src/lonora_api/routes/secret_cards.py:105-113`, validated by `lonora_security.network.compatible_endpoint`). After the owner types the key, the server sends it to that URL (`follow_model`, then every routed call).
- Probe: `compatible_endpoint` accepts `http://169.254.169.254/latest`, `http://postgres:5432`, `http://api:8000/v1` and `https://evil.example/v1`.
- The card does show the Server URL, but the hint is `connectHint` («ما تكتبه يذهب مباشرة إلى الخادم: لا يدخل المحادثة ولا يصل إلى أي وكيل», "What you type goes straight to the server: it does not enter the chat or reach any agent"). Beside a "Server URL" line, "the server" reads as that endpoint, and the hint says nothing about the key also being a workspace secret usable by commands (Q14 (b)).
- Fix:
  - refuse link-local (169.254/16, fe80::/10) and Lonora's own Compose service names for card URLs;
  - give `model_provider` its own hint in Arabic and English: the key is sent to the Server URL shown and is usable by commands in the workspace.

### L2 (low): the endpoint URL and the key can come apart
- `lonora_providers/credentials.py:46-49`: the card's saved `model_endpoint:` setting always beats `LONORA_OPENAI_COMPATIBLE_BASE_URL`, but the key is "newest DB row, else deployment".
- After `DELETE /secrets/{id}` of the card's key, the deployment's key is sent to the agent-proposed URL.
- Fix: clear the `model_endpoint:` setting when its key is deleted, or store the URL with the key's secret id and use them only as a pair.

## Rejected (one line each)
- The "Replaces" line misses a provider-scope key: cosmetic, and covered by M1's fix.
- Agent can choose the destination scope: no. Field, role and workspace destination are fixed by `CONNECTING["model_provider"]`; extra fields are refused (tested).
