## Findings

### H1. After 200 woken trades in the window, new closes never wake their owner (5.5.2)
- **Where:** `packages/trading/src/lonora_trading/close_wake.py:152-170`.
- **What:** the query orders by `created_at` ascending and applies `.limit(MAXIMUM_PER_PASS * 4)` (200) before it skips trades that already have a `close-wake:` receipt (`:169-170`). Once 200 trades in the 2-day window are woken, every pass reads the same 200 rows and wakes nobody. A new close stays unreachable until the old rows leave the window. By then it has usually left the window itself, so its wake is lost for good.
- **When it happens:** a scalping team, or one stop-out of many positions, reaches this.
- **Reproduced:** by the subagent's probe, which wrote 200 woken trades plus 1 fresh close and ran three passes. Output: `woken 0 broker_event runs 0 fresh woken: False`. I confirmed the order of limit and skip by reading the code.
- **Fix:** exclude woken trades in SQL, so the limit applies only to unwoken rows. Add `~exists(select(EffectReceiptRow.key).where(EffectReceiptRow.key == literal(WAKE_KEY) + ClosedTradeRow.id))` to the `where`. `_redirect_unread` needs the same treatment: filter on owner and status in SQL before its limit. Add a test with more than 200 woken trades followed by a fresh close.

### M1. A close wake can never end silently: every closed trade posts a chat message (11.5, 5.5.2, 0.4)
- **Why:** the wake is a `broker_event` Run, and `is_conversational("broker_event")` is True (`packages/core/src/lonora_core/run_state.py:33`).
  - An empty final turn gets the `no_answer` nudge (`tool_loop.py` near `:597`).
  - `group_silence` is refused outside groups.
  - `return_outcome` posts the final reply to the agent's conversation (`outcome_return.py:167-209`).
- **Effect:** 5.5.2 puts the self-review in memory, but every close also posts a message such as "Saved my review." A stop-out of 50 positions posts 50 messages.
- **Reproduced:** by the subagent's probe. The model wrote memory, tried `group_silence`, returned empty, got the nudge, and its final line was posted.
- **Context:** the old attributed broker-event wake already behaves this way. This PR adds a new per-trade wake source on top of it.
- **Fix:** mark close-wake Runs (for example metadata `quiet: true`). For those Runs, skip the `no_answer` nudge and allow an empty final answer, which `outcome_return` already posts nothing for. Add "reply only if something needs the owner" to the wake text.

### M2. An untrue comment, and a permanent skip for a deleted agent's close (0.4, 3.1.2)
- **Where:** `close_wake.py:172-174` says "The agent no longer exists: its tickets went to Lonora (3.1.2)".
- **Why it is wrong:** nothing transfers tickets at this commit (W-TEAM's step), and the ledger row keeps the deleted agent's id. The close of such a ticket writes a permanent `skipped: agent_missing` receipt and wakes nobody.
- **Fix:** wake Lonora (`personal_agent_id`) when the agent is gone, the way `broker_recovery` falls back to the personal agent. At minimum, make the comment true and do not write a permanent skip receipt.

### L1. One Run per trade, with no batching
- A 50-position stop-out creates 50 Runs and 50 work threads. `MAXIMUM_PER_PASS` paces the work but caps nothing (P1 holds once H1 is fixed).
- Optional: one wake per agent per pass, listing its closed trades.

## Rejected (one line each)
- Backfill: the window `created_at > now-2d AND closed_at > now-2d` keeps a first read's old history from waking anyone (tested with a 30-day-old close). Closes in the two days before deploy do wake, which is fine. Say so in the PR body.
- Closes during a gateway outage longer than 2 days are never woken: an operational edge, noted.
