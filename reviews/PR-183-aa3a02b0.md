## Findings

### M1. Once its Settle card is superseded, an ambiguous operation has no deterministic way to be settled (6.8, 14.1.1)
- **The removed route was the fallback.** `POST /trading/journal/{id}/resolve` settled any ambiguous row. The card surface does not re-raise a card it has lost:
  - `owner_cards.py:86-98` raises a card only on a `trading.operation_updated` event.
  - `raise_system_card` (`owner_actions.py:1725-1727`) uses a stable id per record, and returns None when any card with that id exists, whatever its status.
  - `renew_card` (`:1818-1823`) renews only `expired` cards.
  - `settle_for_delete` (`:2211-2257`) supersedes every pending card in a deleted conversation.
  - The delete guard (`obligations.py:37-68`) covers only operations attributed to runs in that thread.
- **Scenario:**
  1. The owner's own run-less order goes ambiguous.
  2. Its card is raised in Lonora's conversation.
  3. The owner deletes that conversation. The delete is allowed.
  4. The card becomes `superseded`. A later event raises nothing, `/renew` returns 409 `owner_action_not_renewable`, and the row stays `ambiguous` and held.
- **Same class:** rows answered "Unknown" on the pre-#96 card (card closed, row ambiguous).
- **Reproduced by me** with `run.sh pr183 python /tmp/claude-0/-home-user-lonorabot/e1b77bc5-dd0b-5073-a830-e13fe9447103/scratchpad/pr183_strand.py`:
  - card `pending`;
  - delete thread 200;
  - card `superseded`;
  - after a new event, still `superseded`;
  - renew 409;
  - journal `ambiguous`;
  - old route 404.
  
  At the base the same sequence ends with the route returning 200 (subagent's run).
- **Why not high:** an agent can still propose a fresh `settle_operation` card (`owner_action_propose`). In the probe that card was decided `not_executed` → `resolved`. Settling therefore now depends on the model choosing to raise it.
- **Fix:** make the card surface self-healing before deleting the fallback (either change suffices; both is safest):
  - **(a)** In `settle_for_delete`, do not supersede a `settle_operation` card whose operation is still ambiguous. Move it to Lonora's conversation, or raise a fresh system card there.
  - **(b)** Add an attention sweep that raises a fresh `settle_operation` card for every ambiguous row with no live pending card. This also covers legacy Unknown-answered rows. Alternatively, let `raise_system_card` and `renew_card` re-raise when the stable-id card is no longer pending and the operation is still ambiguous.
  
  Add a core-check assertion: delete the thread holding the card, then a pending card exists again.
