## Verified finding

### M1 (medium): push receipts confirmed before the upgrade stall the receipt check for good
- `packages/gateway/src/lonora_gateway/push.py` `check_receipts` selects the 100 oldest `push:%` effect receipts that are `confirmed` with no `delivery` (`order_by(created_at).limit(100)`). A row is due only if `confirmed_at` is 15 minutes old, and a missing `confirmed_at` defaults to now.
- Pushes confirmed before this commit have a `ticket_id` but no `confirmed_at`. So they are never due and never closed (the `RECEIPT_KEPT` "unknown" close also needs `confirmed_at`), and they stay in the oldest-100 window forever.
- A row whose `ticket_id` is empty never gets due either.
- Once an installation has 100 such rows, no newer push's receipt is ever read, so a phone Apple or Google report gone is never removed. Below 100, the check still rescans them on every push tick.
- Reproduced on PostgreSQL: 100 legacy rows (`confirmed`, `ticket_id`, no `confirmed_at`) plus one new row confirmed 20 minutes ago with a delivered receipt waiting. After three `check_receipts` passes: `ASKED [] | new delivery: None | legacy delivery: None`.
- Fix:
  - Treat a missing `confirmed_at` as the row's `created_at`, so legacy rows are read or closed as unknown after a day.
  - Close a confirmed row without a `ticket_id` at once (`delivery: "no_ticket"`).
  - Optionally filter the query to rows that are due, so not-yet-due rows cannot fill the window.
  - Add the legacy case to `test_push_sender.py`.

## What I checked
- **Secrets:** the receipt keeps only the token's hash (`token_hash`), never the token. The Expo access token goes only in the `Authorization` header and is never logged. A failed lookup returns silently and is retried, and it never sends a push.
- **Deletion:** a phone is deleted only for `DeviceNotRegistered`, and only when it still holds the same `device_id` and `token_hash`, so a re-registered phone with a new token is kept. The row is locked `FOR UPDATE` while it is updated.
- **Adapter:** `receipts()` posts ids only, with no redirects. 4xx/5xx and malformed bodies raise `push_receipts_failed` / `push_response_invalid`, and only dict receipts are kept.
