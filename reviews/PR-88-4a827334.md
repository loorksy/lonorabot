The lead's main concern holds: provisioning never opens a trading connection and never changes the trading SDK instance (details under "What I checked").

## Verified findings

### M1 (medium): a retried create can make a second MetaApi account (6.3 spirit; a billed duplicate)
- `packages/adapters/src/lonora_adapters/brokers/metaapi_provisioning.py:261-273`
- The SDK draws a new random `transaction-id` on every `create_account` call. The client never supplies a stable one, so recovery rests only on `find()`.
- Failure case: the answer is lost (the SDK turns a read timeout into `ApiException`), or the SDK's 10-minute `202` wait expires. If the account is not listable yet, `find` returns None and the call raises. The caller's retry then POSTs again under a new transaction-id.
- Probe (real SDK `HttpClient` over a scripted transport): two attempts sent different ids, `['ubrufhwd…', 'ycxykwnb…']`.
- The module docstring (lines 9-11) knows a retry "would be a second account", but relies on `find` rather than MetaApi's own idempotency key.
- Fix: the caller persists one create transaction-id (per owner, login and server) before the first POST, and every attempt sends it. Issue the POST through `metatrader_account_api._metatrader_account_client` / its `_http_client.request` with headers `{'auth-token': token, 'transaction-id': stable_id}`, then `get_account(id)`. Add a test that two attempts carry the same id.

### M2 (medium): an account MetaApi created can come back as a refusal, and `created=True` is lost; the `REFUSALS` comment is untrue
- `metaapi_provisioning.py:49-59` and `265-267`
- The SDK's `create_account` POSTs and then reads the account with `get_account`. If that follow-up read fails with 429, 401/403 or 409, the error maps to a `REFUSALS` code and is re-raised without a look, though the account exists.
- Probe: POST 201 `acc-1`, then the read got 429, and the result was `CREATED BUT RAISED: broker_rate_limited`.
- The comment "Failures after which MetaApi certainly did not create the account" is therefore untrue (0.4). The next call finds the account but returns `created=False`.
- Fix: classify refusals from the POST's own answer only. Make the POST yourself via `_metatrader_account_client.create_account`, then treat any failure of the follow-up read as "created, look again".

### L1 (low): a read timeout never maps to `broker_provisioning_timeout`
- `metaapi_provisioning.py:140-144`: the SDK converts `httpx.ReadTimeout` into `ApiException(None, None, url)`, so the `httpx.TimeoutException` branch is dead for SDK calls.
- Probe: `READ TIMEOUT CODE: broker_provisioning_unavailable ApiException`. Safe, since `find` still runs.
- Fix: map `ApiException` with `status_code is None` to the timeout code, or drop the dead branch.

### L2 (low, 0.4): a docstring describes a caller that does not exist yet
- `metaapi_provisioning.py:236-239`: "The caller holds the owner's connection lock and persists the MetaApi id before it deploys." No caller exists at this commit.
- Fix: word it as a requirement: "Callers must hold the owner's connection lock and persist the MetaApi id before deploying."

### L3 (low): the real-SDK test does not assert that no websocket opens
- `tests/test_metaapi_provisioning.py:251-336`: the no-terminal-connection property is checked only by a source scan, the `ENTITY_CALLS` allow-list and a fake entity.
- Fix: in the real-SDK test, patch the SDK socket client's `connect` to raise, or assert `provisioning.api._metaapi_websocket_client._socket_instances` is empty afterwards.

## Rejected
- No second `broker.execute` path: the only caller is still `execution.py:576`.
- No token or password leak: errors pass through `safe_exception_message` with the secrets, `ProvisionedAccount` keeps the login out of its repr, and tests assert caplog is clean.

## What I checked
- The client builds its own `sdk.MetaApi(token, ...)`; constructing it opens no socket.
- Calls used: account list, get, create, and entity deploy/undeploy/redeploy/remove/update, through the `ENTITY_CALLS` allow-list. No `get_rpc_connection`, `get_streaming_connection`, `connect`, `wait_connected` or order call.
- The trading instance keeps `_timeout`/`_retries` (tested).
- The provisioning host is the SDK's fixed `mt-provisioning-api-v1.agiliumtrade.agiliumtrade.ai`. `validate_sdk_url` enforces https, `*.agiliumtrade.ai`, port 443 and no userinfo. The token goes only in `auth-token`, and account (non-JWT) tokens are refused.
- The password update re-sends the stored update fields.
- Tests: tests/test_metaapi_provisioning.py gives 14 passed; ruff, ruff format and pyright are clean. The client is unwired at this commit (acceptable under 0.4, apart from L2).
