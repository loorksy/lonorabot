## Finding 1 (medium): "wakes Lonora once" fails when the reason flaps within one outage

- File: `packages/db/src/lonora_db/system_alerts.py:80`, `run_id = stable_id(item.owner_id, "system-alert:" + item.id)`. The wake is keyed on the item, and at this head's base every flap raises a new item.
- Evidence: probe on a fresh database with one account and one `since`, the reason alternating timeout and 401 over 6 ticks. Output: `lost items 3 token items 3 wakes lost 3 wakes token 3`, i.e. 6 Lonora runs for one outage.
- Rebasing on attn/1 01b65ebb (one open item per outage) reduces this to at most one wake per distinct problem, but the wake key still depends on item identity.
- Fix: rebase on 01b65ebb, and key the wake on the problem:
  - broker codes: `system-alert:<code>:<account_id>:<since>`
  - uncertain operation: `system-alert:operation_uncertain:<operation_id>`
  - Add a flapping test asserting one run per (code, since), and fix the doc line "Its id is derived from the item, so it never runs twice".

## Finding 3 (low): a failed or skipped wake is never retried

- Files: `system_alerts.py:73-78` logs a failure and `:81-84` skips a paused Lonora. The callers never come back: the event receipt is recorded, and the health path sees the item exists. An alert still open after Lonora is resumed never reaches it (3.1.5).
- Also, an `operation_uncertain` item raised by the quarantine path (`gateway/attention.py:402-411`) has parameters `{"reason_code": "attention_projection_failed"}` and no `operation_id`, so `alert_prompt` returns None and Lonora is never woken.
- Fix: on each tick, attempt the wake for open alert items that have no wake run (the stable id keeps it idempotent), and give the quarantine item enough context to be woken for, or document that it is not.
