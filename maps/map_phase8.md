### 1.4 Connect flow and failure cases
- `connect_account` (`connections.py:32-105`): uniqueness pre-check (`:42-43`), `verified_identity` (`:21-29`) which builds a `MetaApiBroker` and reads `metadata_identity` (`metaapi.py:283-298`: login, server, broker, name, platform from the MetaApi account entity, no RPC), backfill of older rows (`:55-97`), then secret + row in one transaction (`:98-104`).
- Rejected token: REST 401/403 maps to `broker_credentials_rejected` (`metaapi.py:66-67`); nothing is stored (secret write is inside the later transaction). Unknown account id: `broker_account_not_found` (`metaapi.py:52-62`).
- Undeployed account: **not checked at connect** (`metadata_identity` does not read `state`). On first use `_prepare_connection` raises `broker_account_undeployed` or `broker_account_not_ready` and **never redeploys** (`metaapi.py:374-383`, comment `:375`); metadata is re-read every 30 s (`:36`, `:263-267`), so it recovers after the owner deploys at metaapi.cloud.
- Owner-facing texts send the owner to the provider: "Start it there, then retry" (`apps/web/src/lib/user_error.ts:168-171`, `apps/mobile/lib/i18n.ts:462-469`). These contradict 9.2.

### 1.5 Keep-alive, health, reconciliation
- One adapter per connection and row version, cached per process (`base.py:38-42`, `:58`); API and gateway each have their own `BrokerManager` (`apps/api/src/lonora_api/runtime.py:25`, `packages/gateway/src/lonora_gateway/runtime.py:51-52`).
- SDK transport is patched process-wide: every HTTP and websocket URL must be `https|wss://*.agiliumtrade.ai:443` (`validate_sdk_url`, `metaapi.py:102-113`), proxy-aware sessions (`:116-129`), reconnect fix (`:170-189`), bounded domain discovery (`metaapi_discovery.py:17-89`). SDK HTTP retries are off (`metaapi.py:211`).
- Connection slots: single-flight creation, failure backoff 2 to 30 s (`metaapi_lifecycle.py:54-90`). Reads retry once after a closed connection (`metaapi.py:426-441`). `execute` never retries: transport failure returns `ambiguous` (`metaapi.py:921-967`).
- Gateway step `account_recovery` every 10 s (`packages/gateway/src/lonora_gateway/service.py:50`, `:186-191`) runs `reconcile_broker_account` for enabled rows (`recovery.py:246-269`): under the account send lock (`:38-44`) it reads account, positions, orders, settles unresolved journal rows (`:77-90`), writes `state.broker_recovery` with `status` connected / degraded / disconnected and `reason_code` = the adapter error code (`:95-128`), emits `broker.recovered` / `broker.degraded` only on a change of (status, reason) (`:136-151`).
- The door refuses new risk while the snapshot status is not connected or degraded: `broker_observation_unavailable` (`packages/trading/src/lonora_trading/admission.py:65`, `:209-230`, called at `execution.py:221-228` and `:421-428`). Exits are admitted.
- Reconciliation history: `reconciliation_evidence` reads positions, orders, deals and history orders from `min(now-7d, submitted_at)`, paged, 15 s cache, refuses truncated or synchronizing history (`metaapi.py:969-1018`); `reconcile` matches `clientId` or broker comment (`:1020-1090`). Gateway steps `reconcile` and `verifications` (`service.py:48-49`).
- What the owner sees on a lost connection: an attention item `broker_degraded` in Lonora's conversation (`packages/core/src/lonora_core/attention.py:16-17`, `:74-80`; `packages/gateway/src/lonora_gateway/attention.py:139-162`, critical when positions or unresolved operations exist). Its text is one fixed sentence whatever the reason (`packages/bus/src/lonora_bus/attention_messages.json:6`, `:56`); only `account_id` is carried, not the reason (`gateway/attention.py:144`). **No agent run is started** by `broker.degraded` (its only consumer is `classify_attention`; the only `trigger="broker_event"` run is for external ticket activity, `recovery.py:232-243`). The reason code is exposed in agent state (`packages/db/src/lonora_db/agent_state.py:369-384`) and on the web `RecoveryPage` (`apps/web/src/shell/agent/RecoveryPage.tsx:20-60`).
- A wrong MetaTrader password is not distinguishable today: the SDK's `account.connection_status` (SDK `metaapi/metatrader_account.py:96`) is never read; it surfaces as a synchronization timeout.

## 9. Design questions the mandate leaves open

**Q1. Where the MetaApi token lives and who reads it.** Options: (a) one owner-level secret, scope `broker`, fixed name, and every MetaApi connection's `secret_id` points to it, so `base.py:55` is unchanged; (b) keep a copy per connection, written by provisioning; (c) a deployment variable. Recommend (a), with a reader that only `BrokerManager` and the provisioning service hold, and the general store refusing reads and deletes of scope `broker`. Ask the owner to confirm that "the execution door" in 7.2.3 means the server-side broker adapter layer: quotes, candles, charts and account reads open the same MetaApi connection with the same token (`base.py:52-56` is the single construction point), so a literal reading would break market data.

**Q2. Whether the broker password is kept after provisioning.** MetaApi stores it; Lonora needs it only for create and for a password update. 7.2.3 says provisioning can read it, which implies it is kept. Recommend keep it encrypted under scope `broker` (needed to re-create an account MetaApi removed); confirm with the owner, since discarding it is the smaller exposure.

**Q3. How provisioning runs without the token entering the workspace.** It must be a server tool; the CLI command set (7.3.2) has no connect command. The open part is where the wait happens (create can take minutes, SDK `http_client.py:91-122`): (a) inside the card-submit request; (b) in a follow-up tool call by the agent (tool timeout cap 600 s, `packages/tools/src/lonora_tools/registry.py:166`); (c) a durable provisioning state on the session row, advanced by a gateway step, which wakes the requesting agent with fixed text at the end. Recommend (c): it survives restarts and does not depend on the model making a second call. (b) is less code; say which you want.

**Q4. Idempotent account creation.** The SDK's transaction id is random per call. Options: (a) before create, list MetaApi accounts and reuse one with the same login and server, all under `lock_owner` (`sessions.py:116-123`); (b) call the provisioning REST endpoint directly with a deterministic transaction id. Recommend (a) (SDK only), and persist the returned MetaApi id before deploy. Pre-check Lonora's own uniqueness with the typed login/server/platform before any MetaApi call (`sessions.py:15-25`, `:133-157`).

**Q5. Account parameters the mandate does not name.** Platform (MT4 or MT5: the agent asks only for number and server), region (`contracts/broker.py:11`), `type`, `reliability` (the high setting uses more MetaApi resource slots, so it costs more), `magic`, `name`. Each needs a default or a question to the owner. I have no basis to choose reliability or region for the owner; ask.

**Q6. Balance report after connecting (16.1).** A fresh account's first synchronization can exceed the adapter's 25 s and 15 s limits (`metaapi.py:395-408`) and then hits the slot backoff. Options: (a) provisioning waits for `wait_connected`, then one `account()` read; (b) the agent waits with `task_wait(kind="broker_recovery")` (`packages/contracts/src/lonora_contracts/tasks.py:109-112`, `packages/db/src/lonora_db/task_wait.py:193-197`); (c) the server wakes the agent on the first `connected` snapshot, whose `account` already holds balance and currency (`recovery.py:95-112`). Recommend (c): broker truth, no polling by the model. Include `investor_mode` and `trade_allowed` (`brokers/normalize.py:100-101`) so an investor password is reported at once instead of at the first order (`packages/trading/src/lonora_trading/preflight.py:22-23`).

**Q7. What "rotate" does to a live connection.** A password update at MetaApi and a token replacement both leave the Lonora row untouched, so cached adapters in both processes keep the old credential (`base.py:38-42`, `metaapi.py:204`) and the door's version fence does not fire (`execution.py:201-202`, `:416-417`). A rotation needs a repository method that bumps `version` and keeps the identity (as `sessions.py:220-224` does), run under the account send lock (`recovery.py:38-44`). Recommend also refusing a rotation that would change login or server: that is a new connection (risk R5).

**Q8. What "disconnect" does at MetaApi.** Today only the row goes. Options: leave the MetaApi account deployed (it keeps billing), undeploy it, or remove it. Recommend undeploy and remove only accounts Lonora provisioned, leave accounts the owner once linked by id, delete the password secret, keep the token. Keep `prepare_delete` first (`routes/trading.py:85-89`).

**Q9. Disable while positions are open.** `enabled=False` makes the door refuse everything, exits included: the check runs before any risk-reducing logic (`execution.py:204-205`). Sections 4.7 and 4.8 keep exits available in every other state. Options: refuse to disable while agent-owned tickets or unresolved operations exist; allow and say so; or let exits through a disabled connection. Ask the owner; recommend the first.

**Q10. Who may trigger connect, disconnect, disable, rotate.** 14.3.5 does not list these under `owner_message_id`. A page or peer message could push an agent to raise a password card for an attacker-chosen server. Recommend: these tools require the run to carry the owner's typed message, and the Secret card shows the login and server the password is for (server text).

**Q11. Fields of a broker-destination card.** 7.2.2 says the agent chooses fields; provisioning must know which value is the password and which the token. Recommend the connect tool fixes the field names for this destination (password; token only when none is saved). Confirm that this satisfies 7.2.2.

**Q12. What counts as one "broker health problem" for push.** The snapshot turns `disconnected` after a single 30 s timeout (`recovery.py:53`, `:113-128`) and is checked every 10 s, so a flapping link can produce many transitions. Options: push every `broker.degraded` transition; push only when a reason persists for N checks; never push for `broker_reconciliation_pending` (the Settle card already pushes). Recommend the last two together; N is the owner's choice.

**Q13. Does Lonora deploy on its own?** 9.4 says "offers to fix". Recommend: Lonora is woken with fixed text naming the reason, proposes the fix in one line, and deploys or raises the Secret card after the owner's reply. The adapter itself keeps never deploying (`tests/test_metaapi_account_readiness.py:63-77` stays green).

**Q14. Provider keys from chat.** P5 removes settings screens; 7.2.3 defines exactly two secret destinations and a model key is neither a broker value nor only a workspace value (the router reads it on the server, `providers/credentials.py:14-18`). Options: (a) a third server destination; (b) the key is a workspace secret that the router also reads (matches "API keys the owner provided", 12.2); (c) deployment variables only. This is the owner's decision; (b) fits the text without a third destination.

**Q15. "OpenAI-compatible endpoints" and "any available model".** Is a provider with an owner-supplied base URL required, or does the phrase describe the existing subclasses? Does "available" mean every model in a connected provider's catalog (`catalog_has`, `packages/db/src/lonora_db/agent_models.py:266`), which would retire the allowed list (`:104`) together with the `agent_model` cards of 10.3.2?

**Q16. Other venues.** "Reports those orders from the venue's own history" and "tells the owner once": agent-composed from the workspace plus one stored per-venue flag, or a server feature? Recommend the former. Does the MCP money classifier (`mcp/policy.py:120-155`) stay as it is? It is not the workspace, so 9.5 does not require changing it.

**Q17. Dormant items.** `BrokerSubscriptionRepository` and `mcp/oauth.py` have no caller and no stated purpose; 13.2 allows deletion only when the mandate removes a feature or a newer implementation replaced it. Ask the owner whether to complete or delete each.

## 11. Risks to the safety core (section 6)

- **R1, one door (6.1).** A provisioning client holds `sdk.MetaApi(token)`, whose account objects can open RPC connections and place orders. Expose only account-entity calls from it, and keep `MetaApiBroker(` constructed in the two existing places (`base.py:52`, `connections.py:22`).
- **R2, never resend (6.3).** The trading instance runs with SDK retries off (`metaapi.py:211`). Provisioning needs the long-running 202 loop; it must use its own SDK instance and never change the trading instance's options. `configure_sdk_transport` patches SDK classes for the whole process (`metaapi.py:191-195`); do not alter it for provisioning.
- **R3, uncertain operations and re-provisioning (6.3, 6.4).** Reconciliation needs a deployed, synchronized account and matches `clientId` or broker comment (`metaapi.py:1043-1044`). Removing and re-creating a MetaApi account while a journal row is `reserved`, `submitted` or `ambiguous` can leave it unreconcilable. Refuse undeploy, remove and re-create while `unsettled_obligation` is true (`packages/db/src/lonora_db/obligations.py:38-66`), the same rule as delete (`:112-115`).
- **R4, send serialization and the version fence (6.6).** Rotation, enable and disable must bump the row version and take the account send lock; closing a cached adapter under a running `execute` produces an `ambiguous` receipt (`metaapi.py:921-967`), correct but it raises a Settle card.
- **R5, account match and ownership (6.5, 3.3.4).** The preflight "account match" compares the adapter's connection id (`preflight.py:20-21`, `normalize.py:92-94`), not the login. Tickets, journal rows and position ownership hang on the connection id. A rotation or re-provisioning that points an existing row at another login or server would silently re-attribute them. `BrokerManager.account` only records an identity change (`base.py:84-91`). Block it.
- **R6, exits (4.7, 4.8).** Disable blocks exits (Q9).
- **R7, secrets (7.2.6).** The adapter redacts token and account id from diagnostics (`metaapi.py:218`, `:245-247`); the password must join that list in the provisioning client, and MetaApi validation errors must not carry the request body into `diagnostic_message`, events or the agent's wake text.
- **R8, a secret deleted while in use.** `DELETE /secrets/{secret_id}` can remove the broker secret of a live connection today; the adapter then fails with `secret_not_found` (`secret_store.py:17-18`, `base.py:55`) while positions are open. 14.3.11 keeps the route; the scope guard of step 2 changes its behaviour for broker secrets, so state it in that pull request.
- **R9, provenance (6.10).** A broker password card raised on the strength of third-party content sends the owner's password to a server name the attacker chose (Q10).
- **R10, core tests.** `tests/test_metaapi_account_readiness.py:63-77` asserts the adapter never deploys; deploy must stay outside `_prepare_connection`. `tests/check_broker_recovery.py:184` asserts one send per invocation.
- **R11, verification environment.** MetaApi hosts are blocked from this session (section 2). Do not loosen `validate_sdk_url` or TLS settings to work around it; live checks need an environment whose policy allows the hosts.
